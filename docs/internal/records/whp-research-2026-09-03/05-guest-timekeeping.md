## 1. Linux x86-64 boot-time clock/timer sequence (kernel 6.x; Alpine `linux-virt` = 6.18.48 per `APKBUILD pkgver`)

### 1(a) `check_timer()` — arch/x86/kernel/apic/io_apic.c

- Returns immediately if `!global_clock_event` (no PIT / HPET-legacy clockevent registered). Skipped when `no_timer_check` is set: `timer_irq_works()` returns 1 without waiting. **`ms_hyperv_init_platform()` sets `no_timer_check = 1`** (mshyperv.c, under `CONFIG_X86_IO_APIC`) — a guest that sees "Microsoft Hv" never runs the IRQ0 probe.
- Setup: `legacy_pic->mask(0)`; `apic_write(APIC_LVT0, APIC_LVT_MASKED | APIC_DM_EXTINT)`; `legacy_pic->init(1)`. `pin1 = find_isa_irq_pin(0, mp_INT)` (the IOAPIC pin the MP/ACPI tables give ISA IRQ0 — pin 2 with the usual IRQ0→GSI2 override); `pin2 = ioapic_i8259.pin` (the pin wired to the 8259 INTR output, normally pin 0).
- Attempt 1: IRQ0 through IOAPIC `pin1`; `timer_irq_works()` → done.
- Attempt 2 (`"..MP-BIOS bug: 8254 timer not connected to IO-APIC"`, `"...trying to set up timer (IRQ0) through the 8259A ..."`): re-route IRQ0 to `apic2/pin2`, `legacy_pic->unmask(0)`, retry.
- Attempt 3 (`"...trying to set up timer as Virtual Wire IRQ..."`): `lapic_register_intr(0)`; `apic_write(APIC_LVT0, APIC_DM_FIXED | cfg->vector)`; `legacy_pic->unmask(0)`. (8259 INTR → LINT0 delivered as a *Fixed* vector.)
- Attempt 4 (`"...trying to set up timer as ExtINT IRQ..."`): `legacy_pic->init(0)`, `legacy_pic->make_irq(0)`, `apic_write(APIC_LVT0, APIC_DM_EXTINT)`, `unlock_ExtINT_logic()`. (True virtual-wire: LINT0 = ExtINT, vector fetched from the 8259 by INTA.)
- All four fail → `panic("IO-APIC + timer doesn't work!  Boot with apic=debug and send a report.  Then try booting with the 'noapic' option.\n")`.

`timer_irq_works()`: `t1 = jiffies; local_irq_enable(); delay_with_tsc()` loops `while ((now - start) < 40000000000ULL / HZ && time_before_eq(jiffies, end))` with `end = jiffies + 4` (comment: "4 GHz == 10 jiffies / 1 GHz == 40 jiffies"); then `return time_after(jiffies, t1 + 4)`. **Requirement: ≥5 IRQ0 ticks must land inside min(4 jiffies of PIT time, 40e9/HZ = 40 M TSC cycles at HZ=1000 ≈ 13 ms at 3 GHz / 10 ms at 4 GHz).** The wait is bounded in *TSC* cycles while the ticks come from the *PIT*: a PIT running slower than TSC-implied real time by more than ~2–2.5× (fewer than 5 one-millisecond ticks in ~13 ms) fails all four attempts → panic. A fast PIT passes trivially.

### 1(b) TSC calibration — arch/x86/kernel/tsc.c

Order: `tsc_early_init` → `determine_cpu_tsc_frequencies(true)` → `x86_platform.calibrate_tsc()` then `calibrate_cpu()`; `tsc_init` retries with `native_calibrate_cpu` after ACPI.
1. `native_calibrate_tsc()`: **Intel only**, CPUID 0x15 (TSC/crystal ratio; crystal Hz in ECX). Crystal Hz != 0 → `setup_force_cpu_cap(X86_FEATURE_TSC_KNOWN_FREQ)` **and `lapic_timer_period = crystal_khz * 1000 / HZ`** ("The local APIC appears to be fed by the core crystal clock") — one leaf pre-empts both the PIT-based TSC calibration *and* the LAPIC calibration, and it hard-binds the LAPIC timer rate to the crystal rate. Falls back to CPUID 0x16 for the crystal. Returns 0 on AMD / no leaf 0x15.
2. `native_calibrate_cpu_early()`: `cpu_khz_from_cpuid()` (0x16) → `cpu_khz_from_msr()` → `quick_pit_calibrate()`.
3. `quick_pit_calibrate()`: needs `has_legacy_pic()`. Programs PIT ch2 mode 0 (`outb(0x61)`, `outb(0xb0,0x43)`, `outb(0xff,0x42)`×2), then `pit_expect_msb()`/`pit_verify_msb()` — each verify is **two `inb(0x42)`** — for up to `MAX_QUICK_PIT_ITERATIONS = 50*PIT_TICK_RATE/1000/256 ≈ 233` MSB decrements (≤ 50 ms), inner loop ≤ 50 000 iterations per MSB. Success: read jitter `d1+d2 < delta >> 11` (**< 500 ppm**). Fail-fast at i==1 if `d1+d2 >= (delta*233) >> 11`, i.e. if ~4 port reads take more than ≈ 233 × 214.6 µs / 2048 ≈ **24 µs** → `"Fast TSC calibration failed"` immediately (the normal outcome on KVM/QEMU). At ~4 µs per PIO exit (this project's measured WHP cost) the fail-fast does *not* trigger (≈16 µs); the loop then needs `i > 152` before the 500 ppm test can pass, so it either succeeds after ~35 ms and ~9–10 k PIO exits or fails on jitter. **Either way ≈10⁴ PIO exits inside 50 ms, 100 % exit-bound.**
4. `pit_hpet_ptimer_calibrate_cpu()` (from `native_calibrate_cpu`): 3 passes of `pit_calibrate_tsc(CAL_LATCH, CAL_MS=10 ms, CAL_PIT_LOOPS=1000)` bracketed by `tsc_read_refs()` (HPET MMIO or `acpi_pm_read_early()` PIO, ≤ `MAX_RETRIES=5`, rejected if the TSC delta across the read exceeds `SMI_TRESHOLD`). `pit_calibrate_tsc` spins on `inb(0x42)` until ch2 reaches zero, needs ≥ `loopmin` iterations, rejects on excessive read-delta spread (`ULONG_MAX`). PIT failed twice → `CAL2_MS = 50 ms` ("This happens in virtualized environments"). Decision: PIT vs HPET/PM inside a **10 % window** → reference value wins ("PIT calibration matches HPET/PMTIMER"); PIT unusable + ref OK → "using HPET/PMTIMER reference calibration"; nothing → 0; PIT OK but >10 % off → `"PIT calibration deviates from %s: %lu %lu"` and **the PIT value wins** ("there are PMTIMERs around running at double speed").
5. `tsc_init()`: frequency 0 → `mark_tsc_unstable("could not calculate TSC khz")` + `setup_clear_cpu_cap(X86_FEATURE_TSC_DEADLINE_TIMER)` → no TSC clocksource, no TSC sched_clock, no deadline clockevent. Else registers `clocksource_tsc_early` (rating 299, `CLOCK_SOURCE_MUST_VERIFY`); `detect_art()` is skipped when `X86_FEATURE_HYPERVISOR`.
6. `init_tsc_clocksource()` (device_initcall): `TSC_KNOWN_FREQ` → register `clocksource_tsc` (300) at once, no refinement. Else `tsc_refine_calibration_work` 1 s later against HPET or PM timer: `|tsc_khz - freq| > tsc_khz/100` (**>1 %**) → refined value *discarded*, early value kept, no unstable mark; else `tsc_khz = freq`, `CLOCK_SOURCE_CALIBRATED`, `lapic_update_tsc_freq()`. With `TSC_KNOWN_FREQ` + `tsc_force_recalibrate`, a >500 ppm deviation only warns. Then `clocksource_tsc` (300, `MUST_VERIFY | HAS_COUPLED_CLOCK_EVENT`) replaces `tsc-early`.
7. Watchdog (kernel/time/clocksource.c): every `WATCHDOG_INTERVAL = HZ>>1` (0.5 s) against the best non-MUST_VERIFY continuous clocksource (hpet 250, else acpi_pm 200). `watchdog_check_freq`: pass iff `abs(wd_delta - cs_delta) < (max_delta >> ppm_shift) + wd_seq`, `SHIFT_4000PPM = 8` by default (**~0.4 %**), `SHIFT_500PPM = 11` when both are `CALIBRATED`; the two reference reads must complete within `WATCHDOG_READOUT_MAX_NS = 50 µs` (3 retries, else `WD_FREQ_TIMEOUT`, "Try again later" — a VMM whose reference-read exit costs >25 µs each never produces a verdict). Skew → `"Marking clocksource 'tsc' unstable due to frequency skew"` → `tsc_cs_mark_unstable` → `"Marking TSC unstable due to clocksource watchdog"` → clocksource switches to hpet/acpi_pm (every `clock_gettime` becomes an MMIO/PIO exit; vDSO falls back to the syscall). `WD_FREQ_NO_WATCHDOG` (no reference clocksource at all) → "Nothing to do": a MUST_VERIFY clocksource is only promoted to `VALID_FOR_HRES` by `clocksource_enable_highres()` on `WD_SUCCESS`, so **with no HPET and no PM timer the TSC is never verified** and the only escape is `tsc_disable_clocksource_watchdog()` (clears MUST_VERIFY).
   - Watchdog off when `X86_FEATURE_TSC_RELIABLE` (`tsc=reliable`, Goldmont, **Hyper-V `HV_ACCESS_TSC_INVARIANT`**) or `CONSTANT_TSC && NONSTOP_TSC && TSC_ADJUST && packages ≤ 4` (`check_system_tsc_reliable`). With it off, a TSC-vs-HPET rate mismatch is *never detected* — the guest drifts silently instead of failing loudly.
8. Fallback ratings: tsc 300, tsc-early 299, hpet 250, acpi_pm 200, jiffies 1. `unsynchronized_tsc()` marks TSC unstable on non-Intel multi-package boxes lacking `CONSTANT_TSC`.

### 1(c) LAPIC timer calibration — arch/x86/kernel/apic/apic.c

- `calibrate_APIC_clock()` **returns 0 immediately if `X86_FEATURE_TSC_DEADLINE_TIMER`**: no calibration; `setup_APIC_timer` registers `"lapic-deadline"` via `clockevents_config_and_register(levt, tsc_khz * (1000 / TSC_DIVISOR), 0xF, ~0UL)` with `CLOCK_EVT_FEAT_CLOCKSOURCE_COUPLED`, `cs_id = CSID_X86_TSC`. `lapic_next_deadline()` = `rdtsc()` + **one `WRMSR MSR_IA32_TSC_DEADLINE`**; `lapic_timer_shutdown` = LVTT write + `WRMSR TSC_DEADLINE, 0`. `apic_validate_deadline_timer()` returns true under `X86_FEATURE_HYPERVISOR` (errata table skipped).
- Else if `lapic_timer_period` is already known (CPUID 0x15 crystal, or Hyper-V `HV_X64_MSR_APIC_FREQUENCY`) → `lapic_init_clockevent()` and return ("Direct calibration methods must have an always running local APIC timer, no need for broadcast timer").
- Else measure: `__setup_APIC_LVTT(0xffffffff, 0, 0)`; poll `LAPIC_CAL_LOOPS = HZ/10` (=100) periods of `tsc_perj = tsc_khz*1000/HZ` cycles (TSC-driven when `tsc_khz` is known, else jiffies) = 100 ms; sample `APIC_TMCCT`, `rdtsc`, `acpi_pm_read_early()` at both ends. `calibrate_by_pmtimer()`: PM delta outside **±1 %** of 100 ms (`pm_thresh = pm_100ms/100`) → `"APIC calibration not consistent with PM-Timer: %ldms instead of 100ms"` and **both the LAPIC delta and the TSC delta are rescaled to the PM timer** ("we trust the PM based calibration if possible"). `lapic_timer_period < 1000000/HZ` → `"APIC frequency too slow, disabling apic timer"`. No PM timer + `global_clock_event` → verify with 100 periodic LAPIC events against jiffies, must be within ±2 of 100, else `"APIC timer disabled due to verification failure"` → `CLOCK_EVT_FEAT_DUMMY` → every CPU ticks from the *broadcast* PIT/HPET clockevent.
- Consequence of rate disagreement: (i) count-down mode only learns a ratio, so LAPIC-vs-TSC disagreement is harmless *unless* the PM timer disagrees with the TSC-measured 100 ms by >1 %, in which case the kernel re-bases on the PM timer and LAPIC events run early/late against TSC-derived time; (ii) TSC-deadline mode has no learning — the deadline is an absolute TSC value, so the virtual LAPIC's comparator **must run on the guest TSC**. An early deadline leaves `hrtimer_interrupt` with nothing expired → reprogram → storm ("hrtimer: interrupt took N ns"); a late one stretches every timer.
- `apic_needs_pit()` (via `i8253.c: pit_timer_init()`/`use_pit()`): the PIT is *not* registered as a clockevent when `ARAT` is set *and* (`TSC_DEADLINE_TIMER` or `lapic_timer_period != 0`); it is **explicitly stopped** (`clockevent_i8253_disable()` — "VMMs otherwise steal CPU time just to pointlessly waggle the (masked) IRQ"). Then `global_clock_event == NULL` and `check_timer()` returns before probing. Advertising ARAT + (TSC-deadline | CPUID 0x15 | Hyper-V APIC frequency) removes IRQ0 from the Linux boot entirely.

### 1(d) Clocksource / clockevent selection
- Clocksource: highest `.rating` among `VALID_FOR_HRES`: `hyperv_clocksource_tsc_page` 500 (250 with `HV_ACCESS_TSC_INVARIANT`), `hyperv_clocksource_msr` 495 (245), kvm-clock 400, **tsc 300**, hpet 250, acpi_pm 200, jiffies 1. vDSO modes `VDSO_CLOCKMODE_TSC` / `VDSO_CLOCKMODE_HVCLOCK` are exit-free in user space; hpet/acpi_pm force the syscall path and one MMIO / one `inl` PIO exit per read (`acpi_pm_read_verified` = 3 `inl` on PIIX4-bug boards).
- Clockevent per CPU: "Hyper-V clockevent" 1000 (`hyperv_timer.c`), `lapic`/`lapic-deadline` 100 (150 with `ARAT`, so it beats per-CPU HPET-MSI 110), HPET legacy 50, PIT `i8253` (global). `CLOCK_EVT_FEAT_C3STOP` (no ARAT) forces broadcast through the global PIT/HPET during idle.

### 1(e) Under a hypervisor — `X86_FEATURE_HYPERVISOR` and the Hyper-V paths
- Generic hypervisor bit only (CPUID.1:ECX[31]): `detect_art()` off; deadline-errata check skipped; `init_hypervisor_platform()` probes vendors. **No recognised vendor leaf → nothing else changes**: PIT/HPET/PM calibration, `check_timer`, watchdog run exactly as on bare metal. Linux boots fine.
- Hyper-V detection (`ms_hyperv_platform`): CPUID 0x40000000 EAX ∈ [0x40000005, 0x4000ffff] and EBX/ECX/EDX == "Microsoft Hv", **and** 0x40000003 EAX has `HV_MSR_HYPERCALL_AVAILABLE` (bit 5) and `HV_MSR_VP_INDEX_AVAILABLE` (bit 6) ("mandatory for all features"); otherwise the generic path. Then `ms_hyperv_init_platform()`:
  - `HV_ACCESS_FREQUENCY_MSRS` (EAX bit 11) `&& HV_FEATURE_FREQUENCY_MSRS_AVAILABLE` (EDX bit 8) → `calibrate_tsc = calibrate_cpu = hv_get_tsc_khz` (`HV_X64_MSR_TSC_FREQUENCY`) + `TSC_KNOWN_FREQ` → **no PIT/HPET/PM calibration, no refinement**; `lapic_timer_period = HV_X64_MSR_APIC_FREQUENCY / HZ` → **no LAPIC calibration**.
  - `no_timer_check = 1` → **no `check_timer()`**.
  - `HV_ACCESS_TSC_INVARIANT` (EAX bit 15) → `wrmsrq(HV_X64_MSR_TSC_INVARIANT_CONTROL, HV_EXPOSE_INVARIANT_TSC)` + `TSC_RELIABLE`; **without it the function tail does `mark_tsc_unstable("running on Hyper-V")`** (after the Hyper-V clocksource is registered, so the TSC page becomes clocksource and sched_clock). Also `hardlockup_detector_disable()`.
  - `x86_platform.apic_post_init = hyperv_init`; installs `HYPERVISOR_CALLBACK_VECTOR`, `HYPERV_STIMER0_VECTOR`, optionally `HYPERV_REENLIGHTENMENT_VECTOR`; `x2apic_phys = 1`; `hv_init_clocksource()`.
  - `hv_init_clocksource()`: TSC page needs `HV_MSR_REFERENCE_TSC_AVAILABLE` (EAX bit 9) → `HV_MSR_REFERENCE_TSC = pfn|1`, registers `hyperv_clocksource_tsc_page` at 10 MHz, `VDSO_CLOCKMODE_HVCLOCK`; MSR clocksource needs `HV_MSR_TIME_REF_COUNT_AVAILABLE` (bit 1). Non-invariant TSC → TSC page also becomes `sched_clock`. (`clocks.rst`: "Linux reads this MSR, skips its own calibration, and marks TSC as reliable"; Hyper-V emulates "the PIT (Generation 1 VMs only), local APIC timer, and RTC — but not HPET".)
  - `hyperv_init()` (`hv_init.c`): `hv_common_init()`; VP-assist pages (`hv_cpu_init` writes `HV_X64_MSR_VP_ASSIST_PAGE` per CPU); `HV_X64_MSR_GUEST_OS_ID`; hypercall page via `HV_X64_MSR_HYPERCALL`; `hv_apic_init()`; hooks `x86_init.timers.setup_percpu_clockev = hv_stimer_setup_percpu_clockev` which calls `hv_stimer_alloc(false)` then the original LAPIC setup ("we can run with the LAPIC timer as a fallback").
  - `hv_apic_init()`: hint `HV_X64_CLUSTER_IPI_RECOMMENDED` (0x40000004 EAX bit 10) → IPIs by `HVCALL_SEND_IPI(_EX)`; hint `HV_X64_APIC_ACCESS_RECOMMENDED` (bit 3) → `eoi = hv_apic_eoi_write` (**lazy EOI: `xchg(&hvp->apic_assist, 0) & 1` → return with no MSR/MMIO at all; else `WRMSR HV_X64_MSR_EOI`**), and in xAPIC mode `read/write/icr` via `HV_X64_MSR_TPR/EOI/ICR`.
  - `hv_stimer_alloc()`: requires `HV_MSR_SYNTIMER_AVAILABLE` (EAX bit 3) **and** `HV_STIMER_DIRECT_MODE_AVAILABLE` (EDX bit 19; Linux uses direct mode only); per-CPU "Hyper-V clockevent", rating 1000, ONESHOT; `set_next_event` = TSC-page read (exit-free) + **one `WRMSR HV_MSR_STIMER0_COUNT`** (absolute 100 ns expiry); oneshot config writes `STIMER0_CONFIG` with `direct_mode=1, apic_vector=HYPERV_STIMER0_VECTOR`. Without both bits Linux "will use a clockevent based on emulated LAPIC timer hardware".
  - VMBus absent: `vmbus_drv.c` binds to the ACPI "VMBus" device (`vmbus_bus_init`/platform probe return `-ENODEV` when it is missing) — the driver simply does not load; timer/clock/APIC enlightenments live in `arch/x86/hyperv` + `drivers/clocksource/hyperv_timer.c` and do not depend on it. **Linux boots.**
  - QEMU/WHPX field notes (`whpx-all.c`): Linux writes `HV_X64_MSR_VP_ASSIST_PAGE` "anyway even when not exposed", and "Windows and Linux both use" `HV_X64_MSR_GUEST_IDLE` (Windows 11 25H2 "even when not advertised") — expect stray synthetic-MSR exits; ignore writes, return 0 on reads.

## 2. Linux idle and steady state

- Tick: `HZ=1000`. `NO_HZ_FULL=y` implies `NO_HZ_COMMON`; with no `nohz_full=` on the cmdline it behaves as NO_HZ_IDLE — idle CPUs stop the tick (no_hz.rst "dyntick-idle"). Busy CPU: 1000 ticks/s = 1000 reprograms + 1000 interrupts + 1000 EOIs. Idle CPU at a login prompt: the next event is the earliest hrtimer/timer-wheel expiry; typically **~10–100 wakeups/s per vCPU** (clocksource watchdog 2 Hz while TSC is MUST_VERIFY, RCU/sched housekeeping, vmstat 1 Hz, getty/syslog/sshd user timers). Assumption: 1–2 vCPUs, no periodic user-space load.
- Per reprogram: TSC-deadline → **1 WRMSR** (`MSR_IA32_TSC_DEADLINE`) + exit-free `rdtsc`; xAPIC one-shot → **1 MMIO write** (`APIC_TMICT`); x2APIC → 1 WRMSR; Hyper-V stimer → 1 WRMSR (`STIMER0_COUNT`) after an exit-free TSC-page read. Per interrupt: 1 EOI (MMIO/MSR) unless Hyper-V lazy EOI elides it. Idle entry/shutdown adds an LVTT write plus a TMICT/DEADLINE zeroing; and one `HV_X64_MSR_GUEST_IDLE` read per idle entry when that MSR is advertised (or attempted anyway).
- Time reads: `tsc` and `hyperv_clocksource_tsc_page` via vDSO — pure `rdtsc`, **no exit**; `hpet` — one MMIO exit per `clock_gettime`; `acpi_pm` — one (or three) `inl` PIO exits per read. The guest must be steered to `tsc` (successful calibration + watchdog-clean or watchdog-off) or to `hyperv_clocksource_tsc_page` (500); anything else costs an exit per time read, and a userland reads time thousands of times per second.
- TSC stays selected only while §1(b)-7 holds: with HPET/PM present and the watchdog on, a TSC-vs-reference skew above ~0.4 % (4000 ppm) in any 0.5 s window demotes the TSC for the rest of the uptime.

## 3. Windows 7 SP1 x64 (and Windows 10/11)

### 3(a) Tick source and QPC source
- **Clock tick.** The Win7-era APIC multiprocessor HAL drives the system clock from the **RTC periodic interrupt (IRQ8) at 64 Hz = 15.625 ms**, raised to 1024 Hz (0.976 ms) when any process calls `timeBeginPeriod(1)` (Windows Internals 6th ed. as quoted in the search results: "the APIC Multiprocessor HAL configures the RTC to fire every 15.6 milliseconds"; Microsoft's QPC page table lists "PC RTC | 64 Hz | 15.625 milliseconds"). Each RTC tick costs the guest a read of CMOS register C (index write + data read = 2 PIO) to acknowledge, plus the LAPIC EOI. **Windows 8+** introduced the dynamic tick (timer coalescing; `bcdedit disabledynamictick`), sourced from the LAPIC timer (TSC-deadline where available) with HPET/RTC as the "platform tick" fallback (`useplatformtick`), so the tick rate is on-demand rather than fixed 64 Hz. Confidence: high for Win7 RTC/64 Hz; medium for Win8+ mechanism details (forum-relayed Windows Internals text, not a primary Microsoft document).
- **QPC source selection** (Microsoft "Acquiring high-resolution time stamps"): Vista/2008 → always HPET or PM timer. Win7/2008R2 → "use TSCs as the basis of QPC on single-clock domain systems where the operating system (or the hypervisor) is able to tightly synchronize the individual TSCs... On systems where the TSC is not suitable for timekeeping, Windows automatically selects a platform counter (either the HPET timer or the ACPI PM timer)". Win8+ → "use TSCs as the basis for the performance counter". Virtualization note: "hypervisors that comply with the hypervisor version 1.0 interface and surface the reference time enlightenment can offer substantially lower overhead", and "when running under a hypervisor that implements the hypervisor version 1.0 interface (or always in some newer versions of Windows), the performance counter frequency is fixed to 10 MHz". Cost: TSC-backed QPC = "10s to several hundred CPU cycles", no kernel transition; platform-timer-backed QPC = "0.8 – 1.0 microseconds" on real hardware and "a system call is required" — in a VM each such call is one MMIO (HPET) or PIO (PM timer) exit.
- **Hypervisor bit → platform timer (Win7).** VFIO post (2016, KVM): "Windows 7 do not use the TSC as a time source if the hypervisor-present bit is set. Instead if falls back on acpi_pm or hpet if hpet is enabled"; measured "3,605ns" per QPC on ACPI PM vs "12.52ns" on TSC; Passmark CPU 3952 → 5594 after hiding the bit (`<feature policy='disable' name='hypervisor'/>`). Under WHP the bit is authorable by the VMM (H0: CPUID leaf 1 is "authored by the host in both directions"), so hiding it is a real option for Win7 — at the price of Win7 also skipping every hypervisor-aware behaviour.
- **Win10/11** under a bare hypervisor bit (no "Hv#1"): community reports (KVM) show high idle CPU from HPET use and cure it with HPET off + `hypervclock` (hv-time); with the reference TSC page Windows uses the 10 MHz enlightened counter exit-free. Genuine Hyper-V "doesn't expose architectural invariant TSC (CPUID.80000007H:EDX[8]) to its guests by default"; the `HV_X64_MSR_TSC_INVARIANT_CONTROL` (0x40000118) / CPUID 0x40000003 EAX[15] pair lets a guest opt in, after which "reenlightenment becomes unneeded" (KVM patch cover letter, "seems to work for modern Windows versions"). Confidence: medium — no primary Microsoft statement on Win10's QPC choice under a non-Hv#1 hypervisor bit was found.

### 3(b) Hyper-V enlightenments Windows consumes (TLFS + QEMU hyperv.rst)

QEMU notes the property "implemented starting from Windows Server 2022 (build 20348)", and that `SeparateSecurityDomain=0` plus dropping IBRS/STIBP/IBPB/SSBD "results in a significant vmexit performance improvement".

### 3(c) Hypervisor bit set, no recognised vendor/interface
Windows keys on 0x40000001 EAX == "Hv#1" ("It is recommended that software only base compatibility decisions on the interface signature reported through leaf 0x40000001"). Without it Windows runs the bare-metal HAL paths but with the hypervisor bit's side effects: Win7 abandons the TSC for QPC (→ HPET/PM timer, one exit per call); no relaxed timing (clock watchdog armed); RTC 64 Hz tick as on hardware. It boots and installs; it is merely exit-expensive and watchdog-fragile.

### 3(d) HAL tick during install
Default 64 Hz (15.625 ms). Setup/WinPE is not a multimedia process; assume 64 Hz unless a component calls `timeBeginPeriod(1)` (then 1024 Hz on Win7, since the RTC divides 32.768 kHz by powers of two — the Win7 "1 ms" request lands at 0.976 ms). Per tick on Win7: CMOS reg C read (2 PIO) + EOI. Win8+ dynamic tick: 64 Hz nominal but coalesced/skipped when idle.

## 4. The "two clocks" hazard

Setting: TSC advances at the host rate (hardware `rdtsc`, or WHP-owned TSC) while PIT / HPET / PM timer / RTC / VMM-owned LAPIC timer advance on a *different* clock (today: an instruction-count clock). Concrete failures, in boot order:

Linux
1. `check_timer` (§1a): the wait is TSC-bounded (40 M cycles), the ticks are PIT-driven. PIT slower than TSC-time by >~2.5× → all four attempts fail → **panic "IO-APIC + timer doesn't work!"**. (Bypassed only by `no_timer_check` — i.e. by the Hyper-V platform — or when the PIT is never registered because ARAT+deadline/known LAPIC rate are advertised.)
2. `quick_pit_calibrate` fails on jitter (normal), then `pit_hpet_ptimer_calibrate_cpu`: PIT-derived and HPET/PM-derived `tsc_khz` disagree by >10 % → "PIT calibration deviates" and the **PIT value is used** → `tsc_khz` wrong by the PIT/TSC rate ratio → `sched_clock`, `printk` timestamps, `udelay`/`mdelay` (`delay_tsc`), `loops_per_jiffy` (`calibrate_delay_is_known` uses `tsc_khz`) all scaled wrong → driver timeouts (ATA/8042 probes) misfire. If PIT and HPET/PM agree with each other but not with the TSC, `tsc_khz` is consistently wrong instead; both cases then hit 3.
3. `tsc_refine_calibration_work` (1 s later, vs HPET/PM) discards a >1 % change and keeps the wrong value; the clocksource watchdog then sees TSC-vs-HPET skew >0.4 %/0.5 s → **"Marking clocksource 'tsc' unstable due to frequency skew"** → clocksource = hpet (an MMIO exit per `clock_gettime`, vDSO disabled), sched_clock degrades. If the watchdog is *off* (TSC_RELIABLE, or CONSTANT+NONSTOP+TSC_ADJUST exposed) the mismatch is never detected and time simply runs fast/slow relative to timers.
4. `calibrate_APIC_clock` (§1c): PM timer disagrees with the TSC-measured 100 ms by >1 % → "APIC calibration not consistent with PM-Timer" → LAPIC ticks-per-jiffy rescaled to the PM timer while time is measured by the TSC → tick period wrong vs wall time → jiffies drift, `sleep 1` ≠ 1 s, RCU stall warnings, soft-lockup false positives (hrtimer watchdog vs sched_clock), OpenRC/service timeouts, TCP RTO, NTP/hwclock disagreement. `-1` jiffies check (no PM timer) → "APIC timer disabled due to verification failure" → broadcast tick from PIT/HPET forever (IPIs per tick).
5. TSC-deadline: an absolute TSC deadline judged by a comparator running on the other clock fires early (hrtimer storm / "hrtimer: interrupt took") or late (every timer stretched). `lapic-deadline` is `CLOCKSOURCE_COUPLED` to the TSC precisely because the two must be the same clock.
6. Hyper-V TSC page: `TscScale`/`TscOffset` computed from a nominal TSC rate that differs from the actual guest TSC rate → reference time drifts against the stimers (which the hypervisor expires on *its* reference time). Under WHP both are hypervisor-owned and consistent; the VMM's device clock must simply be the same host time base.

Windows
7. Win7 `KeStallExecutionProcessor` and the TSC synchronisation/calibration checks at boot ("Windows checks if the TSC is suitable for timing purposes and performs the necessary frequency calibration") are made against the PIT/PM timer; a TSC that calibrates to a rate inconsistent with the platform timers is declared unusable → QPC on HPET/PM (slow), and stall loops mis-timed → storage/USB init timeouts ("Starting Windows" hangs, installer stalls at driver load).
8. Windows system time advances by the RTC/LAPIC tick count (device clock) while QPC/`GetSystemTimePreciseAsFileTime` derive from the TSC (Win8+): the two drift apart → UI timers and media playback misbehave, W32Time slews, installers' progress/"time remaining" and `WaitForSingleObject` timeouts skew.
9. Clock watchdog: Windows bugchecks **0x101 CLOCK_WATCHDOG_TIMEOUT** when "an expected clock interrupt was not received on a secondary processor... within the allocated interval" — a tick source that stalls or lags relative to TSC-based expectation on an MP guest trips it; the `hv-relaxed` hint exists specifically to disable this class of watchdog in VMs.
10. Pause/resume: if the TSC keeps running while the device clock (and HPET/PM/PIT) stops — or vice versa — Linux's watchdog sees a step (→ TSC unstable) and Windows sees QPC jump against ticks. `WHvSuspendPartitionTime` ("suspends time for the partition. No virtual processor may be running... Time will resume when `WHvResumePartitionTime` or `WHvRunVirtualProcessor` is called", 1903+) stops every hypervisor-owned clock (TSC, reference counter, synthetic timers, in-hypervisor APIC timer) as a unit; QEMU wraps `WHvSetVirtualProcessorRegisters(WHvX64RegisterTsc)` in it "to reduce the variance in TSC across vCPUs". OpenVMM's `VmTime` is "a VM-specific timeline, which monotonically increases when and only when the VM is running... based on an offset from the OS's monotonic clock while the VM is running, and a fixed time when the VM is not running" — the device clock must be that, and the suspend/resume of both must be atomic with respect to guest execution.

**The invariant:** every guest-visible clock — TSC, LAPIC timer / TSC-deadline, PIT, HPET, ACPI PM timer, RTC (periodic + update), Hyper-V reference counter / TSC page / synthetic timers — is a fixed-ratio function of ONE monotonic host time base, that base advances only while the VM runs, and all advertised frequencies (CPUID 0x15/0x16, `HV_X64_MSR_TSC_FREQUENCY`, `HV_X64_MSR_APIC_FREQUENCY`, HPET period register, PIT 1.193182 MHz, PM 3.579545 MHz, RTC 32.768 kHz, reference 10 MHz) are the true ratios. Pausing = `WHvSuspendPartitionTime` + freezing the device time base for the identical span; resuming = `WHvResumePartitionTime` + re-anchoring the device base, with the Hyper-V TSC page `TscSequence` bumped if `TscScale`/`TscOffset` changed.

## 5. Per-second exit budget (estimates)

Assumptions common to all: 1 vCPU unless stated; one VMM exit ≈ 4 µs of host time (H0 measured: port 4.0, MMIO 4.3, halt 4.0 µs); "exit" = a return from `WHvRunVirtualProcessor` to the VMM — hypervisor-internal intercepts (synthetic MSRs, in-hypervisor APIC MMIO/MSR, HLT under an in-hypervisor APIC) are **not** counted; interrupt injection from the device thread (`WHvRequestInterrupt`) is not an exit but may cause one interrupt-window exit when the guest has IF=0. Device exits (disk, console, keyboard) are shown separately because they dominate and are independent of the clock design. Configurations: **(i)** no enlightenments, LAPIC in hypervisor, HPET present, TSC clocksource; **(ii)** no enlightenments, LAPIC in the VMM (every LAPIC MMIO/MSR access exits, HLT exits to the VMM, every injection is a register write); **(iii)** Hyper-V enlightenments (reference TSC page + stimer + APIC assist + frequency MSRs + TSC_INVARIANT + guest-idle), LAPIC in hypervisor.

## 6. Legacy real-mode / BIOS phase

Bochs BIOS (`cpp_orig/bochs/bochs/bios/rombios.c`):
- **IRQ0 at 18.2 Hz via the 8259:** `int08_handler` updates the BDA tick count, chains INT 1Ch, `call eoi_master_pic` (`out PORT_PIC1_CMD, al`) → **1 PIO exit per tick ≈ 18/s**, plus one injection.
- **INT 15h/86h (microsecond wait):** "currently using the refresh request port 0x61 bit4, toggling every 15usec" — `int1586_tick: in al, PORT_PS2_CTRLB ... jmp int1586_tick`: a tight `inb(0x61)` loop, **one PIO exit per iteration ≈ 250 k exits/s for the whole duration of any BIOS delay** (at 4 µs/exit). The 15 µs toggle must be derived from host time; if the toggle is derived from an instruction-count clock, each poll (one instruction, one exit) makes the toggle look slow and every BIOS delay stretches. ATA/ATAPI detection and reset paths spin on the status port the same way (`await_ide`).
- **INT 15h/83h (RTC wait interval):** unmasks IRQ8 and turns on the RTC periodic interrupt (1024 Hz) → **~1 k injections/s**, and the INT 70h handler reads CMOS reg C + EOIs both PICs → **~4 PIO exits per IRQ ≈ 4 k/s** while an interval is armed (DOS-era software; not used by Linux/Windows loaders).
- **INT 16h AH=00h/10h (wait for key):** `int16_wait_for_key: cli; mov ax,[0x1a]; cmp ax,[0x1c]; jne ...; sti; jmp` — a pure memory spin on the BDA buffer head/tail with one `INT 15h AX=9002h` device-wait hook. **Zero exits**, but the vCPU never halts (100 % busy in hardware); only IRQ0 (18/s) and IRQ1 arrive. INT 1Ah/00h reads the BDA tick count — memory only.
- **ISOLINUX/SYSLINUX menu:** its idle routine executes `HLT` unless `NOHALT 1` is configured, so the menu wait is a HLT (parks in the hypervisor with an in-hypervisor APIC; one halt exit to the VMM ≈ 4 µs otherwise) woken 18 times a second. **bootmgr** polls INT 16h/01h (memory) — assume a busy spin like the BIOS wait; not verified.
- **VGA BIOS teletype (INT 10h/0Eh):** per character one 0xB8000 write (an MMIO exit if VGA memory is trapped) plus cursor programming via 0x3D4/0x3D5 (≈4 PIO) → **≈5 exits/char**; a boot menu of ~2 KB ≈ 10 k exits once.

**Can a legacy 8259 IRQ0 reach a guest whose LAPIC the hypervisor owns?** `WHV_INTERRUPT_TYPE` is `Fixed=0, LowestPriority=1, Nmi=4, Init=5, Sipi=6, LocalInt1=9` — **there is no ExtINT and no LocalInt0** (WHvRequestInterrupt doc). crosvm therefore refuses `DeliveryMode::External` ("WHPX does not support requesting an external interrupt"). All three VMMs synthesise the 8259's INTA themselves and inject the resulting vector on the BSP:
- **QEMU `whpx-all.c`** (kernel-irqchip, `WHvX64LocalApicEmulationModeX2Apic`): `whpx_vcpu_pre_run` waits for `vcpu->ready_for_pic_interrupt` (set by a `WHvRunVpExitReasonX64InterruptWindow` exit, armed via `WHvX64RegisterDeliverabilityNotifications.InterruptNotification`), takes the vector with `cpu_get_pic_interrupt(env)` and writes `WHvRegisterPendingEvent = { EventType = WHvX64PendingEventExtInt, Vector }`, then `whpx_vcpu_kick_out_of_hlt` clears `WHvRegisterInternalActivityState.HaltSuspend` ("to get out of HLT we either have to request an interrupt or manually get it away from HLT"). IOAPIC/MSI interrupts go through `whpx_send_msi` → `WHvRequestInterrupt` with `Type = delivery mode`; level-triggered EOIs come back as `WHvRunVpExitReasonX64ApicEoi` → `ioapic_eoi_broadcast`. Without kernel irqchip: `WHvRegisterPendingInterruption { WHvX64PendingInterrupt, vector }` plus a CR8 sync.
- **OpenVMM `virt_whp/apic.rs`** (offloaded APIC): LINT0 assert → `extint_pending`; `inject_extint` reads `Rflags`, `InterruptState`, `PendingInterruption`, `PendingEvent`; if not ready, arms `DeliverabilityNotifications(priority 0)`; else `dev.acknowledge_pic_interrupt()` (INTA emulated in the VMM) and writes `HvX64PendingExtIntEvent` into `PendingEvent` together with `InternalActivityState = 0` ("TEMPORARY: force the processor out of the halted state — otherwise, the hypervisor delays injecting the interrupt"). LINT1 (NMI) uses `WHvX64InterruptTypeLocalInt1`.
- **crosvm `irqchip/whpx.rs` + `vcpu.rs`** (split irqchip): PIC vectors go **only to vcpu 0**, via `WHvRegisterPendingInterruption { WHvX64PendingInterrupt, vector }` when `ready_for_interrupt()` (last exit's `Rflags.IF`, no `InterruptShadow`, no `InterruptionPending`), else it requests an interrupt window; IOAPIC → MSI → `WHvRequestInterrupt`.
Consequences: (1) the guest's LVT0 programming (`check_timer` toggles it between masked-ExtINT, Fixed-vector and ExtINT) is **not honoured by the platform** — the VMM must read/track LVT0 (via `WHvGetVirtualProcessorInterruptControllerState2` or the `X64ApicWriteLint0ExitTrap` extended exit) if it wants fidelity, otherwise a PIC interrupt is delivered even while the guest believes LINT0 is masked; (2) H0 measured `InternalActivityState` as unwritable under `LocalApicEmulationMode::None`, whereas QEMU and OpenVMM write it under the in-hypervisor APIC modes — mode-dependent, re-verify under XApic/X2Apic before relying on either result; (3) the PIT's 1 kHz Linux tick during the PIT→LAPIC hand-over and the BIOS's 18.2 Hz IRQ0 both cost a VMM→hypervisor register write per tick plus an interrupt-window exit whenever the guest has IF=0 at the moment of injection.

Also relevant for §5(i): WHP exposes the in-hypervisor APIC timer frequency as `WHvCapabilityCodeInterruptClockFrequency` / `WHvPartitionPropertyCodeInterruptClockFrequency` (QEMU defaults `HYPERV_APIC_BUS_FREQUENCY = 200 MHz` and overrides from the capability; crosvm hard-codes 100 MHz with the comment "we don't know what the right frequency is here, but 100MHz gives us better results than the frequency that WSL seems to use, which is 500MHz"). No WHP processor-feature bit for TSC-deadline exists in the mirrored `WHV_PROCESSOR_FEATURES` definitions and Hyper-V guests do not list `tsc_deadline_timer`; assume the in-hypervisor LAPIC offers **count-down mode only**, so Linux will calibrate it (100 ms, PM-timer-checked) unless CPUID 0x15 or `HV_X64_MSR_APIC_FREQUENCY` names its rate — and whatever rate is named must equal `InterruptClockFrequency`.

## Invariants the VMM must keep
1. **One time base.** TSC, LAPIC timer (count-down and any deadline comparator), PIT, HPET, ACPI PM, RTC periodic/update, Hyper-V reference counter / TSC page / stimers all derive from one monotonic host time base that advances only while the VM runs; each at its nominal fixed ratio (PIT 1.193182 MHz, PM 3.579545 MHz, RTC 32.768 kHz, HPET per its period register, reference 10 MHz).
2. **Advertised frequencies are true frequencies.** CPUID 0x15/0x16 and `HV_X64_MSR_TSC_FREQUENCY` must match the real guest TSC rate to <500 ppm (Linux warns at 500 ppm with `TSC_KNOWN_FREQ`; the watchdog demotes at 4000 ppm / 500 ppm calibrated). `HV_X64_MSR_APIC_FREQUENCY` and any CPUID 0x15 crystal value must equal the LAPIC timer's real rate (`InterruptClockFrequency` when the APIC is in the hypervisor) — Linux sets `lapic_timer_period = crystal/HZ` from leaf 0x15.
3. **PIT, HPET and PM timer agree with each other (±10 % for calibration acceptance) and with the TSC (±0.4 % per 0.5 s, else TSC is demoted).** Practically: exactly, since they share the base.
4. **Reference reads are fast or absent.** Two consecutive HPET (or PM) reads must complete within 50 µs of TSC time (each exit <~25 µs) or Linux's watchdog never verifies the TSC and stays on the slow reference. Prefer no HPET (ACPI `HPET` table absent → acpi_pm becomes the watchdog, 1 PIO exit per read) or mark the TSC reliable (TSC_INVARIANT / CONSTANT+NONSTOP+TSC_ADJUST).
5. **TSC-deadline only if the comparator runs on the guest TSC.** Never set CPUID.1:ECX[24] unless the LAPIC model (or the hypervisor) compares against the guest-visible TSC; never set CPUID.6:EAX[2] ARAT unless the timer keeps running through HLT (always true in a VM).
6. **PIT stop semantics.** Linux stops the PIT (`clockevent_i8253_disable`) when it does not need it; the PIT model must stop firing (no phantom IRQ0 to inject).
7. **Pause is atomic across clocks.** `WHvSuspendPartitionTime` (no VP running) + freeze the device time base for the identical wall span; resume both together; bump the TSC page `TscSequence` if scale/offset change; keep vCPU TSCs synchronised (write TSC only while partition time is suspended, as QEMU does).
8. **Legacy interrupts.** 8259 output reaches a hypervisor-owned LAPIC only as a VMM-synthesised ExtINT/vector event on the BSP (no `WHV_INTERRUPT_TYPE` for it); the VMM performs INTA and must honour LVT0 mask/mode (trap `X64ApicWriteLint0`) and arm the interrupt window when IF=0.
9. **Hyper-V leaf consistency.** Expose "Microsoft Hv"/"Hv#1" only with HYPERCALL + VP_INDEX MSRs (else Linux ignores the leaves); every 0x40000003 bit advertised must be backed by the WHP synthetic feature bank; use `HV_ACCESS_TSC_INVARIANT` so Linux prefers the native TSC and disables the watchdog; the 0x40000004 hints (bits 3, 5, 10) must match what is implemented; stimer direct mode (EDX bit 19) is required for Linux's clockevent, classic mode for older Windows.
10. **QPC monotonicity for Windows.** TSC identical across vCPUs, never stepping backwards across pause/resume or vCPU migration; HPET/PM counters monotonic and 64-bit-wrap-correct.

Without enlightenments the next-cheapest shape is (i): APIC in the hypervisor, TSC clocksource kept by exposing invariant TSC (CPUID 0x80000007 EDX[8]) + CONSTANT/NONSTOP + `TSC_ADJUST` (watchdog off) or by keeping HPET reads under 25 µs; CPUID 0x15 on Intel to skip the 20 k-exit PIT burst — with the LAPIC rate then pinned to the crystal value; and ARAT so the PIT is stopped and `check_timer` is skipped. Windows 7 stays at 2–10 k exits/s on QPC in that shape unless the hypervisor bit is hidden.
