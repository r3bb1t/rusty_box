## KBC-2 [imprecise/minor] §3.2 divergences, lines 166-167
- spec: Bochs runs a continuous 150 µs timer whose handler returns early when nothing is pending.
- source: The continuous 150 µs timer is confirmed (see KBC-1). The 'returns early' description is true in substance but elides what the handler does BEFORE the early return, which matters for the one-shot replacement: every fire of `timer_handler` calls `periodic(1)`, and `periodic` first snapshots and clears `irq1_requested`/`irq12_requested` (lines 1041-1045), and only then returns early if `timer_pending == 0` (lines 1047-1049); `timer_handler` then raises IRQ1/IRQ12 from that snapshot (lines 1032-1035). So 'nothing pending' must mean BOTH `timer_pending == 0` AND no IRQ request latched — a fire with `timer_pending == 0` but `irq1_requested == 1` still does real work (raises IRQ1). Consequence: a byte transferred to `outb` on fire N sets `irq1_requested` (line 1072-1073) and the IRQ is raised on fire N+1, one period later — so the one-shot must re-arm after the LAST byte's transfer even when the queue is then empty. The spec's fast-mode arming rule ('whenever a byte is enqueued or an IRQ1/IRQ12 request is latched') already covers this, so no design decision is wrong, but the phrase 're-armed while the queue is non-empty' alone would be insufficient. Also note the second early-return branch (`usec_delta < timer_pending`, lines 1051-1056) is dead in practice: `activate_timer` only ever sets `timer_pending = 1` (lines 1100-1102) and the handler always passes `usec_delta = 1` (line 1030), so every fire after an `activate_timer` performs the transfer.
- evidence: cpp_orig/bochs/bochs/iodev/keyboard.cc:1025-1036: `void bx_keyb_c::timer_handler(void *this_ptr) { ... retval=class_ptr->periodic(1); if (retval & 0x01) DEV_pic_raise_irq(1); if (retval & 0x02) DEV_pic_raise_irq(12); }` — keyboard.cc:1038-1049: `retval = (Bit8u)BX_KEY_THIS s.kbd_controller.irq1_requested | (BX_KEY_THIS s.kbd_controller.irq12_requested << 1); BX_KEY_THIS s.kbd_controller.irq1_requested = 0; BX_KEY_THIS s.kbd_controller.irq12_requested = 0; if (BX_KEY_THIS s.kbd_controller.timer_pending == 0) { return(retval); }` — keyboard.cc:1051-1056: `if (usec_delta >= ... timer_pending) { timer_pending = 0; } else { timer_pending -= usec_delta; return(retval); }` — keyboard.cc:1072-1073: `if (BX_KEY_THIS s.kbd_controller.allow_irq1) BX_KEY_THIS s.kbd_controller.irq1_requested = 1;` — keyboard.cc:1098-1103: `void bx_keyb_c::activate_timer(void) { if (... timer_pending == 0) { ... timer_pending = 1; } }`
- correction: Bochs runs a continuous 150 µs timer (the `serial_delay` default) whose handler, on every fire, first collects and clears any latched IRQ1/IRQ12 request and raises it, and then returns early when no serial transfer is pending (`timer_pending == 0`). A byte moved to the output buffer on one fire has its IRQ raised on the next fire, one period later — so the fast-mode one-shot must be armed on every byte enqueue AND on every IRQ1/IRQ12 latch, including after the last queued byte is transferred.

## PCS-3 [imprecise/major] §3.2 Mechanics
- spec: "the wheel's existing multi-fire catch-up (`countdown_event`'s `while time_to_fire <= ticks_total` loop) handles several deadlines in one step. No per-tick loop, no periodic kicker." (spec lines 139-141).
- source: The cited `while` loop does the opposite of multi-firing: it COALESCES missed periods into a single fire. In `countdown_event`, a due continuous timer is marked triggered exactly once (`*triggered_flag = true;`, pc_system.rs:738) and then the loop only walks `time_to_fire` forward past `ticks_total` (pc_system.rs:744-746); the dispatch step records that owner once per triggered flag (`self.record_fired_owner(owner);`, pc_system.rs:783). So if `ticks_total` overshoots a 150 µs timer by 10 periods, the loop yields ONE fire and 9 deadlines are dropped, not "several deadlines handled". What actually replays several deadlines in one call is `tickn`'s own outer loop, `while remaining >= self.curr_countdown { remaining -= self.curr_countdown; self.curr_countdown = 0; self.countdown_event(); }` (pc_system.rs:694-699), which invokes `countdown_event` once per countdown period spanned — one fire per period, per deadline. A second, orthogonal multiplicity is `countdown_event`'s scan over every registered timer (pc_system.rs:733-762), which fires all DISTINCT timers due at the same instant. The design's conclusion (`tickn(elapsed)` on a device-thread wake catches the wheel up over many deadlines without a per-tick loop) survives, because `tickn` is O(deadlines crossed), not O(ticks) — but it survives on a different mechanism than the one cited, and the cited one has the drop semantics a catch-up plan must account for.
- evidence: rusty_box/src/pc_system.rs:738-746 `*triggered_flag = true; if !self.timers[i].flags.contains(TimerFlags::CONTINUOUS) { ... } else { // Continuous: advance time_to_fire past ticks_total\n while self.timers[i].time_to_fire <= self.ticks_total { self.timers[i].time_to_fire += self.timers[i].period; }` — one `triggered_flag`, N period advances. And rusty_box/src/pc_system.rs:694-699 `while remaining >= self.curr_countdown { remaining -= self.curr_countdown; self.curr_countdown = 0; self.countdown_event(); }`.
- correction: "the wheel's existing catch-up handles several deadlines in one step: `tickn` calls `countdown_event` once per countdown period spanned (`pc_system.rs:694-699`), and each `countdown_event` fires every distinct timer that is due (`pc_system.rs:733-762`). Note that `countdown_event`'s inner `while time_to_fire <= ticks_total` loop (`pc_system.rs:744-746`) coalesces rather than replays: a continuous timer whose deadline was overshot by N periods is recorded as ONE fire (`pc_system.rs:738, 783), so the device thread must not let `ticks_total` jump past a periodic deadline by more than one period where the guest counts edges (PIT IRQ0). No per-tick loop, no periodic kicker."
