### 1.2 APIC mode decision (`vmm_core/virt_whp/src/lib.rs` 1443-1525) — H
```rust
let user_mode_apic = user_mode_apic || config.hv_config.as_ref().is_some_and(|_| !offload_enlightenments);
let lapic = if user_mode_apic { LocalApicKind::Emulated(virt_support_apic::LocalApicSet::builder()…build()) } else { LocalApicKind::Offloaded };
let apic_mode = if !user_mode_apic { match apic_mode() { XApic => WHvX64LocalApicEmulationModeXApic, X2Apic* => WHvX64LocalApicEmulationModeX2Apic } } else { WHvX64LocalApicEmulationModeNone };
```
Default (`openvmm/hypervisor_resources/src/lib.rs` 72-79): `user_mode_apic: false, offload_enlightenments: true` → **the hypervisor's APIC is the default**; `user_mode_apic` is an opt-in CLI parameter (`openvmm_hypervisors/src/whp.rs`). In user-mode-APIC mode they additionally set `X64MsrExitBitmap(ApicBaseMsrWrite | UnhandledMsrs)` and `ExceptionExitBitmap(#GP)` because "the hypervisor incorrectly fails to exit to the parent" for synic MSRs (1518-1524).
Always: `X64MsrExit`; `GpaAccessFaultExit` — "because WHP tries to handle these for ROM regions, resulting in an extra syscall and C++ exception for each such exit" (1553-1558). With `hv_config`: `HypercallExit` (not on nested), `X64CpuidExit`; when enlightenments are offloaded **and** the APIC is offloaded: `UnknownSynicConnection | RetargetUnknownVpciDevice` plus `SyntheticProcessorFeatures` = HypervisorPresent, Hv1, AccessVpRunTimeReg, AccessPartitionReferenceCounter, AccessHypercallRegs, AccessVpIndex, **AccessPartitionReferenceTsc, AccessSynicRegs, AccessSyntheticTimerRegs**, FastHypercallOutput, ExtendedProcessorMasks, SyntheticClusterIpi, NotifyLongSpinWait, QueryNumaDistance, SignalEvents, RetargetDeviceInterrupt, TbFlushHypercalls, AccessGuestIdleReg, AccessFrequencyRegs, …, AccessIntrCtrlRegs, DirectSyntheticTimers (1583-1680). I.e. **synic, stimers, reference-TSC page and hypercalls are implemented by the hypervisor**; OpenVMM only services vmbus ports via notification ports/doorbells (`synic.rs`: `create_notification_port`, `signal_synic_event`, `register_doorbell`). The user-mode `hv1_emulator` path is used only when enlightenments are not offloaded (vp.rs 294-320 scans `hv.synic.scan(ref_time_now, …)` and arms a VmTime timeout).

### 1.3 Run loop and threading (`virt_whp/src/vp.rs` 228-390, `vmm_core/src/partition_unit/vp_set.rs`) — H
One `VpRunner` per VP (`VpSet::add`), driven on a caller-provided thread; `run_vp` is an `async fn` that loops: `interrupt.maybe_yield().await` → `poll_fn` (check stop, publish the task waker into `inner.waker`, `vmtime.cancel_timeout()`, scan synic/message queues/start-VP requests, `process_apic(dev)`, arm `vmtime.poll_timeout(cx)`; returns `Pending` while halted) → `sync_lazy_eoi()` → `runner.run()` (= blocking `WHvRunVirtualProcessor`, `vm/whp/src/lib.rs` 1727) → `handle_exit`. vp_set.rs 1245-1250: "Since `run_vp` will block the thread until it receives a cancellation notification, always poll the other sources to exhaustion before polling the future." Cancellation sources: `RunnerCanceller` and `Partition::request_yield` → `NeedsYield::request_yield()` + `cancel_run()` on both VTLs (lib.rs 669-690); `ensure_vtl_runnable` cancels only for VTL>0 (493-499). `wake()` (501-505) only calls `waker.wake_by_ref()` — it does **not** cancel a running VP. With the hypervisor APIC `process_apic()` is a stub returning `true` (vp.rs 1751-1753) and HLT never exits (the hypervisor blocks the VP inside `WHvRunVirtualProcessor`).

### 1.4 Exit table (`vp.rs` 548-610) — H
IoPortAccess→`handle_io_port` (`emulate_io` fast path, else x86emu); Cpuid→`handle_cpuid`; ApicEoi→`dev.handle_eoi(vector)` (IOAPIC EOI); MsrAccess→`handle_msr` (APIC MSRs to the user-mode LAPIC, unknown → inject #GP via `PendingEvent`); InterruptWindow→`handle_interrupt_window` (clears the DeliverabilityNotifications shadow); Hypercall; MemoryAccess→`handle_memory_access` (`emulate_mnf_write_fast_path` for bit-set on monitor pages, else x86emu); SynicSintDeliverable; Canceled→counter only; UnrecoverableException→triple fault; InvalidVpRegisterValue→fatal; Halt→`self.state.halted = true` (user-mode APIC) ; Exception.

### 1.5 Interrupt delivery, both APIC kinds (`virt_whp/src/apic.rs`) — H
`WhpPartitionInner::interrupt(vtl, MsiRequest)` (75-116): **Offloaded** → decode MSI address/data into `WHV_INTERRUPT_CONTROL {type, dest mode, trigger, destination, vector}` → `WHvRequestInterrupt`; then `ensure_vtl_runnable` (no-op for VTL0). **Emulated** → `lapic.request_interrupt(addr, data, wake_for_apic)` sets IRR in `virt_support_apic`, `wake_for_apic` = `scan_irr.store(true, Release); wake()`; on the VP task's next `poll_fn`, `process_apic` → `lapic.apic.scan(vmtime, scan_irr)` → `inject_interrupt` (657-720): one `get_registers!` of Rflags, Cr8, InterruptState, PendingInterruption, PendingEvent; if deliverable, write `WHvRegisterPendingInterruption` and `acknowledge_interrupt(vector)`; else set `DeliverabilityNotifications{interrupt_notification, priority}` and wait for the InterruptWindow exit. PIC/LINT0 (39-73, 516-604): Offloaded → `extint_pending=true; vp.wake()`; `inject_extint` reads Rflags/InterruptState/PendingInterruption/PendingEvent, if ready `dev.acknowledge_pic_interrupt()` then writes `PendingEvent` (ExtInt) + `InternalActivityState=0` — "TEMPORARY: force the processor out of the halted state--otherwise, the hypervisor delays injecting the interrupt"; LINT1 → `WHvRequestInterrupt(LocalInt1)`. Consequence (M): in user-mode-APIC mode an interrupt raised while the VP is inside `WHvRunVirtualProcessor` is injected only at the next natural exit; only the offloaded path reaches a running VP.

### 1.6 MMIO/PIO emulation and register access (`virt_whp/src/emu.rs`, `vmm_core/virt_support_x86emu`, `vm/x86/x86emu`) — H
`x86emu::Cpu` trait (cpu.rs) is per-register (`gp/set_gp/xmm/rip/segment/efer/cr0/rflags`) plus async `read_memory/write_memory/compare_and_write_memory/read_io/write_io`. `WhpEmuCache { gps: [u64;16], segs: [SegmentRegister;6], rip, rflags, cr0, efer }` is fetched **once per emulated exit** with a single batched `get_registers!` (`emulator_state()`, emu.rs 388-466), served from the cache, XMM fetched lazily per register (110-122), written back with a single `set_registers!` in `flush()` (468). Instruction bytes and the initial GVA→GPA translation come from the exit context (`instruction_bytes`, `initial_gva_translation`); a one-entry GVA→GPA cache lives in `EmulatorCpu` (emulate.rs 567-710). No shadow CPU anywhere.

### 1.7 Lazy state — H
`AccessVpState` (`vp_state.rs`) exposes registers/activity/xsave/apic/debug_regs by category, used for save/restore/inspect only. The run loop names exactly the registers it needs (`get_registers!`/`set_registers!` lists); the only user-mode shadows are `WhpEmuCache` (per exit) and `deliverability_notifications` per VTL. Hyper-V owns the state; there is no dirty-mask register file.

### 1.8 Time (`vm/vmcore/src/vmtime.rs`) — H
Module doc: "This is a VM-specific timeline, which monotonically increases when and only when the VM is running … Internally, this clock is based on an offset from the OS's monotonic clock while the VM is running, and a fixed time when the VM is not running." and "This is related to the idea of the hypervisor reference time, but it is not guaranteed to be the same value". `VmTime(u64)` in 100 ns; `TimeState::Started(Timestamp{vmtime, os_time}) | Stopped(vmtime)`; `VmTimeKeeper::start/stop` (state unit, `vmtime_unit.rs`); `VmTimeAccess::{now, set_timeout, set_timeout_if_before, cancel_timeout, poll_timeout(cx)}` (804-870), one host `PollTimer` deadline = `timestamp(next).os_time()` (229-242); `VmTimerPeriodic`. TSC: `tsc_frequency()` partition property feeds `ReferenceTimeSource` with `is_ref_time_backed_by_tsc: false` (lib.rs 1291-1300); with offloaded enlightenments reference time = partition `ReferenceTime` property (1960-1964), otherwise `VmTimeReferenceTimeSource` = `vmtime.now().as_100ns()`. `WHvX64RegisterTsc` is not manipulated in the run loop (M).

### 1.9 Devices (`vm/chipset_device/src/poll_device.rs`, `vm/devices/chipset/src/{pit,ioapic}/mod.rs`, `vm/vmcore/src/line_interrupt.rs`) — H
`PollDevice::poll_device(cx)`: "called asynchronously whenever the device enters the running state, and then whenever wake_by_ref is called on the waker … The device will only be polled while in the running state." PIT: `PitDevice { vmtime: VmTimeAccess, timers: [Timer;3], last: VmTime }`; `evaluate(now)` converts elapsed VmTime to PIT ticks, timer 0 output → `LineInterrupt::set_level(out)` (189); `poll_device` = `if Ready(now) = vmtime.poll_timeout(cx) { evaluate(now); arm_wakeup() }` (588-598); `arm_wakeup` = `vmtime.set_timeout_if_before(next_wakeup)`. IOAPIC: `LineInterruptTarget::set_irq(n, high)` → `assert(routing, n)` → `Box<dyn IoApicRouting>::assert(n)`; redirection-entry writes call `routing.set_route(n, Some((msi_addr, msi_data)))` (291). `emuplat/ioapic.rs` adapts to `virt::irqcon::IoApicRouting`; `virt_whp` (lib.rs 2052-2067): `set_irq_route` stores in `IrqRoutes`, `assert_irq` → `irq_routes.assert_irq(irq, |req| self.interrupt(Vtl0, req))`. `LineInterrupt` (line_interrupt.rs) fans one logical line out to N `LineSetTarget`s (IOAPIC and PIC both).

### 1.10 End-to-end "PIT fires → IRQ0 → IOAPIC → LAPIC → guest" on WHP, default config — H
1. **Device task thread**: host `PollTimer` fires at the host instant of the PIT's VmTime deadline → `PitDevice::poll_device` → `evaluate` → counter-0 `out` rises → `LineInterrupt::set_level(true)`.
2. **Same thread**: `LineSetTarget::set_irq` on IOAPIC (and PIC) → `IoApicDevice::assert` → `IoApicRouting::assert_irq(2)` → `IrqRoutes` MSI → `WhpPartitionInner::interrupt(Vtl0)` → **`WHvRequestInterrupt`** (Fixed/Edge, dest, vector).
3. **Hypervisor**: the in-hypervisor APIC sets IRR and injects into the running VP. **The VP thread is never stopped, cancelled or synced** (no `cancel_run` on this path); a VP halted in HLT is unblocked inside `WHvRunVirtualProcessor`.
4. **VP thread**, level-triggered routes only: guest EOI → `ExitReason::ApicEoi` → `dev.handle_eoi(vector)` → IOAPIC re-asserts if the line is still high. Edge (PIT) needs no exit.
Legacy PIC mode: PIC → `ApicLintLineTarget::set_irq` → `pulse_lint(vp0, LINT0)` → `extint_pending; wake()` → injected by `inject_extint` at the next exit / while halted (the DeliverabilityNotifications window covers IF=0). A 50 ms `VTL2_TIMER_PERIOD` periodic wake exists only for VTL2 configs: "only the hypervisor knows that interrupts are pending" (vp.rs 278-292).

## 2. Hyperlight (hyperlight-dev/hyperlight) — `src/hyperlight_host/src/hypervisor/virtual_machine/whp.rs`, `surrogate_process*.rs`, `hypervisor/mod.rs`, `docs/cancellation.md`

### 2.1 Shape — H
Single VP, no devices, no OS: docs/hyperlight-execution-details.md — "Hyperlight offers little more than a CPU and memory … In a loop, tell previously created vCPU to run until we reach a halt message, one of several known error states, or an unsupported message". The old `hypervisor_handler` thread is gone; today `HyperlightVm` runs the vCPU on the caller's thread (`hyperlight_vm/mod.rs` run loop, 600-790) and `InterruptHandle::kill()` is the only cross-thread entry point.

### 2.2 Partition setup (`whp.rs` 283-336) — H
`WHvCreatePartition` → `ProcessorCount = 1` → (feature `hw-interrupts`) `check_lapic_emulation_support()` (bit 1 of `WHvCapabilityCodeFeatures`) and `LocalApicEmulationMode = XApic` (1279-1290) → `WHvSetupPartition` → `WHvCreateVirtualProcessor(p, 0, 0)` → `init_lapic_bulk`: "Individual APIC register writes via `WHvSetVirtualProcessorRegisters` fail with ACCESS_DENIED on WHP when LAPIC emulation is enabled, so we use `WHvGet/SetVirtualProcessorInterruptControllerState2` to read-modify-write the entire LAPIC register page" (1293-1296). LAPIC init (`hw_interrupts.rs` 116-124): SVR enabled + spurious 0xFF, TPR 0, LDR/DFR flat, LINT0/LINT1/LVT-timer/LVT-error masked — "LVT Timer (0x320): masked — host timer thread injects instead". No CPUID/MSR exits by default; `set_debug()` toggles `ExtendedVmExits = 1<<2` (ExceptionExit) + `ExceptionExitBitmap(#DB|#BP)` only under gdb (1137-1177). MSR access is via named registers (`0x10 => WHvX64RegisterTsc`, `TscAdjust`, `TscAux`, `TscDeadline`; 90-99) — no `WHvX64RegisterTsc` writes in the run path; single-step = RFLAGS.TF (1181-1190).

### 2.3 Run loop (`whp.rs` 512-676) — H
`loop { WHvRunVirtualProcessor(partition, 0, &ctx) ; match ctx.ExitReason { X64IoPortAccess => { RIP += InstructionLength; port==VmAction::Halt → return Halt; hw-interrupts: PIC/PIT/speaker/0x80 OUTs are swallowed, `PvTimerConfig` OUT starts a timer thread; else return IoOut(port, data[..access_size]) } ; X64Halt => { if timer active { continue } else return Halt } ; MemoryAccess => MmioRead/MmioWrite(gpa) ; Canceled => Cancelled ; Exception (gdb) => Debug{dr6} ; _ => Unknown } }`. Quote (597-603): "With software timer active, re-enter the guest. WHvRunVirtualProcessor will block until the timer thread injects an interrupt via WHvRequestInterrupt, waking the vCPU from HLT." I/O values are read from the exit context (`IoPortAccess.Rax`), never from a register fetch.

### 2.4 Timer / interrupt injection without a PIC (`hw_interrupts.rs`, `whp.rs` 1365-1408) — H
`TimerThread::start(period, inject_fn)` = `std::thread::spawn(|| while !stop { sleep(period); inject_fn() })` (192-208); for WHP `inject_fn` = `WHvRequestInterrupt(partition, WHV_INTERRUPT_CONTROL { _bitfield: 0 /* Fixed, Physical, Edge */, Destination: 0, Vector: 0x20 })` (1385-1399). "Hardcoded timer interrupt vector. The guest remaps IRQ0 to vector 0x20 via PIC ICW2, so we use that same vector directly — no PIC state machine needed." Period clamped to 100 µs..10 s. PIC EOI (OCW2 non-specific on port 0x20) is bridged to the LAPIC by `do_lapic_eoi()` = read the 1 KiB page with `InterruptControllerState2`, clear highest ISR bit, write it back (1365-1375). So: **timer on a host thread, delivery into the hypervisor APIC via `WHvRequestInterrupt` while the VP runs or is halted; the VP is never cancelled for a timer.**

### 2.5 Cancellation (`docs/cancellation.md` 250-291, `hypervisor/mod.rs` 38-78, 153-170, 300-360) — H
`InterruptHandle::kill()` = `state().set_cancel(); common_kill()`; state is a packed `AtomicU8` (RUNNING_BIT=1<<1, CANCEL_BIT=1<<0, DEBUG bit). Windows: "No signal loop: Windows calls `WHvCancelRunVirtualProcessor()` at most once in `kill()`, without needing retries" because the API "sets an internal `CancelPending` flag … Set immediately by the API call; Checked at the start of each VM run loop iteration (before entering guest mode); Automatically cleared when it causes a `WHvRunVpExitReasonCanceled` exit". Hence "we only call `WHvCancelRunVirtualProcessor()` after checking that `RUNNING_BIT` is set … If called when not running, the API would still succeed and will unconditionally cancel the next run attempt". Linux needs the `SIGRTMIN` retry loop (default 500 µs) because a signal landing before `ioctl(KVM_RUN)` is lost. The run loop treats `Cancelled` with `!cancel_requested` as stale and retries ("Windows: WHvCancelRunVirtualProcessor called right after vcpu exits but RUNNING_BIT is still true", hyperlight_vm/mod.rs 751). `SynchronousInterruptHandle` holds an `RwLock<(dropped, T)>`: "`kill()` takes a read lock before calling `WHvCancelRunVirtualProcessor`; `set_dropped()` takes a write lock … ensuring no `kill()` is accessing the partition when `WHvDeletePartition` is called" — otherwise "use-after-free causing STATUS_ACCESS_VIOLATION or STATUS_HEAP_CORRUPTION" (mod.rs 311-326).

### 2.6 Surrogate processes and `WHvMapGpaRange2` (`surrogate_process_manager.rs` 40-160, `whp.rs` 401-460, 1434-1470) — H
Why: `WHvMapGpaRange` "returns the following error when called more than once from the same process: … (0xC0370008) ERROR_VID_PARTITION_ALREADY_EXISTS". Workaround: `WHvMapGpaRange2(partition, process_handle, src, dest, size, flags)` where the memory is a `CreateFileMapping/MapViewOfFile` view inside a do-nothing `hyperlight_surrogate.exe`; "There is a limit of 512 partitions per process" — `HARD_MAX_SURROGATE_PROCESSES = 512`, documented as "The absolute hard limit on surrogate processes imposed by the `WHvMapGpaRange2` API (512 process handles per calling process)". Pool of 512 pre-spawned processes in a kill-on-close job object; `HYPERLIGHT_MAX_SURROGATES=0` falls back to plain `WHvMapGpaRange` "single-VM-per-process mode" guarded by `NoSurrogateGuard`. `WHvMapGpaRange2` is `GetProcAddress`-loaded: "only available on Windows 11 or Windows Server 2022 and later". docs note: "The use of surrogates is a temporary workaround on Windows until WHP allows us to create more than one partition per running process" — **the limit still exists in the current tree** (H). Matches our own measurement (memory: "ONE partition per PROCESS").

### 2.7 Numbers — H (blog), M (applicability)
Nov-2024 blog: Wasmtime sandbox "< 0.03 milliseconds", Hyperlight micro-VM "1-2 milliseconds", traditional VM "> 120 milliseconds" to create. Feb-2025 blog: "0.0009 seconds on average" per warm function call (1,000 requests, 5 connections), achieved by pre-loading the guest, pre-allocating stack/heap/IO buffers, pre-creating the partition with memory mapped and the vCPU initialised. `docs/benchmarking-hyperlight.md` sample: `sandboxes/create_sandbox time: [33.803 ms 34.740 ms 35.763 ms]` (Criterion example output, platform unspecified). No published WHP-vs-KVM latency split; the only qualitative statement is the cancellation doc above.

## 3. wtf (0vercl0k/wtf) — `src/wtf/whv_backend.{h,cc}`, README, doar-e blog "Building a new snapshot fuzzer & fuzzing IDA"

### 3.1 Partition setup (`whv_backend.cc` 101-260) — H
`WHvCreatePartition` → `ProcessorFeatures` = host `WHvCapabilityCodeProcessorFeaturesBanks.Bank0` ("This was added because of `issues/252`; the VM had access to speculation control settings (MSR) but not setting `ProcessorFeatures` meant that a default state was being used … when the guest was attempting to write that MSR, it triggered a #GP") → `ProcessorCount = 1` → `ExtendedVmExits.ExceptionExit = 1` only → `ExceptionExitBitmap = #DE | #DB | #BP` → `WHvSetupPartition` → `WHvCreateVirtualProcessor(Partition_, 0, 0)` → `LoadState` → `PopulateMemory`. **No `LocalApicEmulationMode` (stays None), no CPUID/MSR exits, no devices, no interrupt controller.** Header comment: "This is the WHV backent. It runs test cases inside an Hyper-V backed VM."

### 3.2 CPU state & TSC (`LoadState`, 262-461) — H
Every register is set one `WHvSetVirtualProcessorRegisters(…, 1, …)` call at a time from the snapshot: GPRs, `Rflags`, **`Tsc`**, `ApicBase`, `Sysenter*`, `Pat`, `Efer`, `Star/Lstar/Cstar/Sfmask`, `KernelGsBase`, `TscAux`, `Cr0/2/3/4/8`, `XCr0`, `Dr0-3/6/7`, `XmmControlStatus`, `FpControlStatus`, `FpMmx0-7`, `Xmm0-15`, segments, `Gdtr/Idtr`, and `PendingEvent = 0` ("Ensure that there's no pending event"). The TSC is simply loaded from the snapshot; there is no RDTSC exit and no TSC re-sync — the guest sees the hardware TSC running from that base. Per-testcase `Restore` re-runs the whole `LoadState` (~60 single-register `Set` IOCTLs; M on the count).

### 3.3 Run loop, timeouts, cancel (`Run`, 761-898; `TimerQ_t`, .h 65-107) — H
`while (!Stop_) { WHvRunVirtualProcessor(...); RunStats_.Vmexits++; switch (ExitReason) { Exception → OnExitReasonException; MemoryAccess → OnExitReasonMemoryAccess; Canceled → { Stop_ = true; TestcaseRes_ = Timedout_t(); } default → print + std::abort(); } }`. Timeout: "This is the small utility class we use to set a time limit; when the timer expires, we cancel the execution of the VP. Stolen from libfuzzer." — `CreateTimerQueueTimer(..., AlarmHandler, ..., Seconds*1000, Seconds*1000, 0)`; `AlarmHandler` → `CancelRunVirtualProcessor()` → `WHvCancelRunVirtualProcessor(Partition_, Vp_, 0)` from the timer-queue thread; `Timer_.TerminateLastTimer()` after each run. So the only cross-thread interaction with a running VP is a wall-clock cancel, and only for the timeout path.

### 3.4 Dirty tracking & restore (`PopulateMemory` 515-538, `OnExitReasonMemoryAccess` 1235-1261, `Restore` 900-931) — H
Current code does **not** use `WHV_MAP_GPA_RANGE_FLAG_TRACK_DIRTY_PAGES` / `WHvQueryGpaRangeDirtyBitmap`: "We map the whole RAM as rx in the EPT. This allows us to track memory writes into pages so that we can restore them. When the partition tries to write to a page set as r-x in the EPT, we get a fault that we handle by keeping track of tracking the dirty GPA as well as remapping the page as rwx." Each first write costs one `MemoryAccess` exit + `WHvMapGpaRange(hva, gpa, 4 KiB, RWX)`; `Restore` copies the dirty pages back and remaps each as R-X again. Blog rationale: "WHvQueryGpaRangeDirtyBitmap was extremely slow for unknown reasons" and "WHvTranslateGva also was slower than expected" → both replaced by hand-rolled versions (`TranslateGva` walks the guest page tables in user space, 637-708).

### 3.5 Breakpoints / single-step (`OnBreakpointTrap` 970-1110, `OnDebugTrap` 1112-1179, `EnableSingleStep` 1411-1445) — H
Coverage = one-shot `0xCC` at basic-block starts from an IDA-generated JSON; regular breakpoints = `0xCC` + handler; step-over = remove `0xCC`, set `RFLAGS.TF`, re-arm on the #DB exit; full trace = TF everywhere + "Make sure SFMASK has the TF bit to 0 to not strip it on 'SYSCALL' instructions" + `0xCC` on all 256 IDT handlers; on the trace path they also clear `InterruptState.InterruptShadow` via `WHvRegisterInterruptState`. Page-in of missing guest pages is done by injecting a #PF through `WHvRegisterPendingEvent` (`PageFaultsMemoryIfNeeded`, 1290-1319).

### 3.6 Numbers — H (quotes), source README 273-295 and the blog
README: bochscpu "~100x slower than KVM when I was fuzzing IDA"; whv "Speed seems to be ok for long executions (lots of bottleneck in whv though; ~10x slower than kvm when I was fuzzing IDA)"; KVM "Fastest for long executions (~500m - 1.5 billion instructions; ~100x faster than *bochscpu*, ~10x faster than *whv*)". README 104: "*bochscpu* is the fastest backend to do that [execution traces], because exiting VMX mode is very expensive on the other backends." Blog console lines: "bochscpu: exec/s: 0.1", "whv: exec/s: 1.5", KVM "exec/s: 12.3" (different hardware). Blog on KVM's edge: "registers available via shared-memory mapping" (kvm_run) and "userfaultfd for on-demand paging" — the per-register IOCTL cost of WHP is the named bottleneck.

## 4. applepie (gamozolabs/applepie) — `bochservisor/src/{lib,whvp,time}.rs`, `bochs/main.cc`, `bochs/cpu/cpu.cc`, README

### 4.1 Shape — H
Rust DLL loaded by a patched Bochs: `BX_CPU_C::cpu_loop()` (cpu.cc 73-89) immediately calls `(*bochs_cpu_loop)(&routines, mem_len, dirty_bits_l1, dirty_bits_l2, ram_base, original_memory)` and returns. `BochsRoutines` (lib.rs 51-89): `set_context`, `get_context`, `step_device(steps)`, `step_cpu(steps)`, `get_memory_backing(addr, typ)`, `cpuid`, `write_msr`, `after_restore`, `reset_all`, `take_snapshot`. Enforced config (main.cc 891-931): `ips=1000000`, `model=corei7_skylake_x` ("designed to be a superset of whatever our hypervisor reports"), `procs=cores=threads=1`, `clock: sync=none`. Partition (whvp.rs 745-795): `ProcessorCount=1`, `ExtendedVmExits = ExceptionExit|X64MsrExit|X64CpuidExit`, `ExceptionExitBitmap = 1<<1` (#DB), **LocalApicEmulationMode never set (block commented out, 754-763)**, memory mapped region-by-region from `getHostMemAddr` with `WHvMapGpaRangeFlagTrackDirtyPages` always on (866-868), BIOS range 0xC0000-0xFFFFF deliberately left unmapped: "There's some weird read/write states we cannot accurately reflect with EPT" (lib.rs 1150-1154). No blog post exists for applepie; README + two YouTube demos are the only author material (WebSearch, M).

### 4.2 When it runs on WHP vs Bochs (lib.rs 1269-1636) — H
`persist.emulating` counts instructions to run in Bochs before the next `WHvRunVirtualProcessor`; `EMULATE_STEPS = 250`, `MAX_EMULATE = 1000`. Exit → action: `MemoryAccess` → `emulating += 250` ("Note this is tunable but 100 seems to by far be the best mix between performance and latency. <10 is unusable. >1000 introduces latency (cursor stutters when moving, etc)"); `IoPortAccess` → +250; `MsrAccess` → +250 (MSRs handled by Bochs); `UnrecoverableException` → +250; `InvalidVpRegisterValue` → +250 ("observed in Windows 7, however if we emulate a bit the issue seems to go away"); `Halt` → +1; `Cpuid` → handled in Rust from `DefaultResult*` with CPUID.1:ECX.XSAVE cleared ("We don't know if we can safely sync these between bochs yet so we disable AVX"); `Canceled` → if `RFLAGS.IF==0` set `DeliverabilityNotifications.InterruptNotification` (`register_interrupt_window`, whvp.rs 828-848); `InterruptWindow` → nothing ("now Bochs knows it can deliver async events and will when we `step_device()`"); new coverage → `emulating += 100`. README: "When MMIO or I/O occurs we run a certain number of instructions under emulation rather than just emulating one. Due to the API costs of entering and exiting the hypervisor, and the likelihood that similar MMIO operations occur next to others, we step a few instructions."

### 4.3 The device-timer mechanism — verbatim (lib.rs 109-146, 1269-1300; main.cc 843-876) — H
Kicker thread: "This thread kicks the WHVP partition approx. 1000 times per second to give us an opportunity to step a bit in Bochs and emulate devices and potentially deliver interrupts. This is _really_ gross but I don't see anything in the WHVP API that has an alternative. Further we use a busyloop here instead of a Sleep() so we can get a higher frequency kick (to get 1000/second this seems necessary)." Body: `advance = tickrate/1000` cycles; `while KICKER_ACTIVE != 0 && rdtsc() < future {}` then `WHvCancelRunVirtualProcessor(handle, 0, 0)`. `KICKER_ACTIVE` is set to 1 only around `hypervisor.run()`.
Top of every loop iteration (1270-1300): `elapsed_cycles = rdtsc() - last_sync_cycles; elapsed_secs = elapsed_cycles / tickrate; elapsed_adj_cycles = (TARGET_IPS * elapsed_secs) as u64; (routines.step_device)(elapsed_adj_cycles);` with the comment "For example if on a 4GHz processor we ran for 1 second, the tick count would be ~4 billion. The `elapsed_secs` would then be ~1.0, which then will be multiplied by the `TARGET_IPS` constant that indicates the Bochs IPS frequency. This gives us an integer value which is the number of cycles in Bochs which corresponds with this same amount of wall-clock time". `TARGET_IPS = 1_000_000.0` is hard-coded.
`step_device` (main.cc 846-876): `TLB_flush()` ("to make sure our dirty bits get updated"), then `while(steps) { if (async_event) { if (handleAsyncEvent()) return; } bx_pc_system.tickn(1); steps--; }` — "We actually tick one at a time even though we could tick in bulk. This allows us to check for async events more frequently and it makes for a lower latency hypervisor experience … Tuning this further might cause interrupts to get queued up without being handled so it could actually potentially cause corruption in the guest." So Bochs's timer wheel is advanced by wall-clock-derived ticks at a fixed 1 MIPS virtual rate, decoupled from instructions executed; there is no per-slice deadline computation, no `WHvGetVirtualProcessorCounters`, and the only "how long to run" bound is the 1 ms kick.

### 4.4 Interrupts — H
README "Interrupts": "Rather than scheduling interrupts to be delivered to the hypervisor we handle _all_ interrupts in Bochs emulation itself … This also gives us features that WHVP doesn't support, like SMIs (for SMM)." Mechanically: devices raise `async_event`; `handleAsyncEvent()` inside `step_device`/`step_cpu` performs the Bochs `interrupt()` (IDT lookup, frame push) on the Bochs CPU; the next `get_context`+`set_context` ships the post-interrupt state into WHP. `WHvRegisterPendingInterruption` is listed but commented out of the context (whvp.rs 142, 252); `deliver_exception` via `PendingEvent` exists (1013-1053) but is only used for the #DB snapshot trigger. `InternalActivityState` is "unknown type" and unused.

### 4.5 State sync — H
Every switch in either direction moves the full `WhvpContext` = 84 `WHV_REGISTER_VALUE`s (whvp.rs 59-148: 16 GPRs, RIP, RFLAGS, 6 segments, LDTR/TR/IDTR/GDTR, CR0/2/3/4/8, DR0-3/6/7, XMM0-15, ST0-7, FpControl, XmmControl, **TSC**, EFER, KernelGsBase, ApicBase, PAT, Sysenter*, STAR/LSTAR/CSTAR/SFMASK, TscAux, XCR0) in one `WHvGetVirtualProcessorRegisters` / `WHvSetVirtualProcessorRegisters` call; Bochs-side `set_context` (main.cc 488-629) writes all of it, then `TLB_flush()`, `handleAlignmentCheck()`, `handleCpuModeChange()`, `handleSseModeChange()`, `handleAvxModeChange()`, and bumps `hypervisor_context_switches` so every icache entry with an older age is re-decoded. TSC: `context->tsc = get_TSC()` out, `set_TSC(context->tsc)` back in — Bochs's TSC is overwritten by the hardware TSC after every run; while in `step_cpu` it advances at 1 tick/instruction (`BX_SYNC_TIME_IF_SINGLE_PROCESSOR`). `applepie_tests/rdtsc_tester` is a bare-metal kernel that panics on "OH NO NON MONOTONIC RDTSC" — the author was testing exactly this seam. `vm_run_overhead` = min of 10,000 empty `run()` calls at start, subtracted from every measured run to estimate cycles truly spent in the guest ("VM run percentage" stat, 1305-1311).

### 4.6 Snapshots / dirty pages — H
Device state = every `bx_shadow_*` registered via `register_state`, merged into contiguous regions and memcpy-restored; RAM restore via `WHvQueryGpaRangeDirtyBitmap` into a 2-level bitmap: "Without this we can do about 65,000 restores/second. With this we can only do about 50. This is a huge performance bottleneck right now and I'm already in an email chain with the WHVP dev to optimize their dirty list API." `after_restore` is disabled ("IRQs get remapped twice, causing a Bochs panic"). VGA framebuffer is not restored; optional `DEVNULL_FRAMEBUFFERS` maps 0xA0000 and 0xE0000000 as plain RAM to kill MMIO exits.

### 4.7 Performance claims — H (absence)
The README contains **no** throughput or "near-native" numbers; the only self-measurement is the printed `VM run percentage`. Author's own assessment (README "Evaluate threading"): "Currently everything happens in one thread which means the hypervisor must exit on an interval to make sure we can step devices. It's as if we wrote our own scheduler." and the planned "falkervisor mode: Extremely fast fuzzing that cancels execution when MMIO or I/O occurs … not supporting things like disk I/O during a fuzz case".

## 6. Design patterns that recur across all of them

1. **`WHvRunVirtualProcessor` is a blocking call owned by one VP thread; the only external lever is `WHvCancelRunVirtualProcessor`.** All six projects use it, and only for *control* (stop/yield/timeout/kill): OpenVMM `request_yield`/`RunnerCanceller`, Hyperlight `kill()`, wtf timeout timer, crosvm `set_immediate_exit`. applepie is the sole project that cancels *periodically for devices* (1000/s kicker), and its author calls that "really gross". Reason: a cancel costs a full exit + re-entry and, in applepie, a full state sync.
2. **Real-OS guests run with the hypervisor's LAPIC (`LocalApicEmulationMode` XApic/X2Apic) and devices inject with `WHvRequestInterrupt` from any thread, without touching the VP.** OpenVMM default, crosvm, Hyperlight hw-interrupts, libwhp. Interrupts reach a running or halted VP immediately; HLT then blocks inside `WHvRunVirtualProcessor` ("Whpx handles VCPU blocking"). Reason: the alternative (user-mode APIC + `PendingInterruption`) is only deliverable at an exit, and OpenVMM's own user-mode path shows exactly that limitation (wake without cancel).
3. **A user-space PIC still coexists with the hypervisor LAPIC.** OpenVMM `inject_extint` and crosvm `WhpxSplitIrqChip` inject PIC vectors via `PendingInterruption`/`PendingEvent(ExtInt)` after checking readiness from the exit context, and arm `DeliverabilityNotifications` when IF=0 to get an `InterruptWindow` exit. Hyperlight avoids the PIC entirely (hardcoded vector 0x20, PIC ports swallowed, PIC-EOI bridged to a LAPIC EOI by rewriting the 1 KiB APIC page). Reason: WHP has no PIC and no ExtInt via `WHvRequestInterrupt` (crosvm: "WHPX does not support requesting an external interrupt").
4. **Device time is host time, paused with the VM, and timers fire on device threads — never on the VP thread and never per-instruction.** OpenVMM `VmTime` (host monotonic + offset, `Started/Stopped`), crosvm PIT worker thread on a host `Timer`, Hyperlight sleep thread; only applepie derives device time from the TSC and converts it into Bochs IPS ticks. Reason: with the CPU on hardware there is no instruction count to drive a wheel from; wall-clock is the only common clock.
5. **The TSC is left to hardware.** Written only at load/restore (`WHvX64RegisterTsc` in wtf `LoadState`, crosvm `restore_timekeeping` preserving the offset); no RDTSC exits (the `X64Rdtsc` exit exists but no one enables it). OpenVMM exposes reference time either as the partition `ReferenceTime` property or as VmTime — explicitly *not* TSC-backed (`is_ref_time_backed_by_tsc: false`). applepie alone round-trips the TSC through Bochs on every switch.
6. **Minimal extended exits.** Everyone sets `ProcessorCount`; CPUID/MSR exits only when the VMM must answer them (OpenVMM `X64MsrExit` always, CPUID only with enlightenments/x2apic; crosvm pre-sets CPUID with `CpuidResultList` and exits only for `CpuidExitList`; wtf/Hyperlight none). Exception exits are enabled only for debugging/coverage (#DB/#BP/#DE, #GP in OpenVMM user-mode APIC). OpenVMM adds `GpaAccessFaultExit` to dodge a per-ROM-write "syscall and C++ exception" inside WinHvPlatform.
7. **MMIO/PIO emulation is single-instruction and register-lazy.** Three implementations: WinHvEmulation callbacks (crosvm, libwhp); OpenVMM's own `x86emu` with a per-exit `WhpEmuCache` (16 GPRs + 6 segs + RIP/RFLAGS/CR0/EFER fetched in one batched Get, XMM on demand, one batched Set on flush; instruction bytes and initial GVA translation taken from the exit context); Bochs itself for 250–1000 instructions (applepie). Nobody keeps a shadow CPU except applepie, and nobody but applepie moves the whole register file per exit.
8. **Register access is by explicit name list, batched, only when needed.** OpenVMM `get_registers!`/`set_registers!` macros, `AccessVpState` by category for save/restore; crosvm reads IF/shadow/pending from the exit context; Hyperlight reads `IoPortAccess.Rax` from the exit context. wtf's per-register single Sets are noted as the WHP bottleneck vs KVM's shared-memory `kvm_run` (blog).
9. **Memory: map big contiguous regions once; dirty tracking is a known sore point.** applepie: `TrackDirtyPages` + `WHvQueryGpaRangeDirtyBitmap` → "65,000 restores/second … With this we can only do about 50"; wtf: abandoned the bitmap API ("extremely slow") for R-X mapping + fault-remap; OpenVMM/crosvm don't use it for run-time. One `WHvMapGpaRange` partition per process (Hyperlight surrogates + `WHvMapGpaRange2`, 512 handles hard limit, Win11/Server 2022+).
10. **Cancel/teardown races are real and handled explicitly.** Hyperlight: `CancelPending` persists to the *next* run ("kill() should have no effect if the vCPU is not running"), stale `Canceled` exits are retried, and an `RwLock` serialises `WHvCancelRunVirtualProcessor` against `WHvDeletePartition` (use-after-free otherwise). OpenVMM: `NeedsYield` flag + cancel so a yield request survives a racing exit.
11. **Enlightenments are offloaded to the hypervisor when it offers them.** OpenVMM's default requests `SyntheticProcessorFeatures` (synic, stimers, reference TSC page, hypercalls, TLB-flush hypercalls) and only services vmbus ports via notification ports/doorbells; the user-mode `hv1_emulator` is the fallback, not the norm.

## 7. Where applepie's approach to Bochs device timers succeeded or failed

**What it is (recap, all H):** one thread; Bochs's `bx_pc_system` timer wheel is kept intact and advanced by `step_device(n)` where `n = TARGET_IPS(1e6) × wall_seconds_since_last_sync` (TSC-derived); a busy-looping kicker thread calls `WHvCancelRunVirtualProcessor` ~1000×/s so the loop regains control; every device interrupt is *taken by the Bochs CPU* (`handleAsyncEvent` inside `step_device`/`step_cpu`) and the post-interrupt architectural state is shipped into WHP by a full 84-register `set`; on every MMIO/PIO/MSR exit Bochs runs 250–1000 instructions before re-entering WHP.

**Where it succeeded**
- Functionally complete with *zero* changes to Bochs devices: PIT/RTC/APIC/PIC/IDE/VGA/e1000 all ran unmodified; SMM/SMI worked ("features that WHVP doesn't support, like SMIs"); Bochs snapshots stayed valid; Windows 10 / Windows 7 / Linux booted (README; the Win7 `InvalidVpRegisterValue` workaround is evidence it was exercised).
- Device time stayed wall-clock-correct on average without any per-slice deadline arithmetic: the wheel is simply caught up to wall time at each kick, so timer drift is bounded by the 1 ms kick period, not by instruction-count estimates. No `WHvGetVirtualProcessorCounters`, no TSC→instruction conversion was needed — the hard problem we are wrestling with (how many instructions until the next Bochs deadline) was side-stepped by making the wheel wall-clock-driven and the slice length fixed.
- The `hypervisor_context_switches` icache-age trick made the shadow-CPU hand-off safe without flushing the whole icache.

**Where it failed / what it cost**
1. Forced 1000 exits/s regardless of guest activity, each paying: cancel exit + `WHvGetVirtualProcessorRegisters`(84) + Bochs `set_context` (+ `TLB_flush`, `handleCpuModeChange`, SSE/AVX mode re-derivation, icache age bump) + `step_device` + `get_context` + `WHvSetVirtualProcessorRegisters`(84) + re-entry. This is structurally the same tax as our "slice bounded by device deadline" design, only with a fixed 1 ms period; it is why the author printed "VM run percentage" as the primary stat and never published a throughput number.
2. Interrupt latency ≥ next kick (up to 1 ms) plus 250–1000 emulated instructions per MMIO exit; the tuning comment ("cursor stutters", "<10 is unusable", ">1000 introduces latency") shows the two knobs fight each other.
3. Time model incoherence: Bochs-internal time runs at exactly 1 MIPS virtual (`ips=1000000` enforced) while the guest's TSC runs at hardware GHz and is written back into Bochs after every run; during `step_cpu` the TSC advances 1/instruction. `rdtsc_tester` exists precisely because this seam produced non-monotonic TSC readings.
4. All interrupt delivery in software means every device interrupt is an exit + full sync + emulation, and nothing can be injected while the VP is on hardware — the opposite of every other project, which uses `WHvRequestInterrupt` into the hypervisor LAPIC.
5. A busy-looping core for the kicker; `WHvQueryGpaRangeDirtyBitmap` restores at ~50/s vs 65,000/s without; `after_restore` unusable ("IRQs get remapped twice").
6. The author's own verdict: "Currently everything happens in one thread which means the hypervisor must exit on an interval to make sure we can step devices. It's as if we wrote our own scheduler." and the planned escape hatch ("falkervisor mode") drops device emulation during fuzz cases altogether.

**What this decides for rusty_box's Bochs timer wheel**
- Keep the wheel *as a data structure* (it is what all Bochs devices program), but stop driving it from instruction counts or from VP slices. Every non-applepie project drives device timers from a host-monotonic clock that pauses with the VM (OpenVMM `VmTime` is the reference design: `Started(Timestamp{vmtime, os_time}) | Stopped(vmtime)`, one host timer armed at `os_time(next_deadline)`, `poll_device` on a device task) — the wheel's `time_ticks` becomes a function of VmTime, `bx_pc_system.tickn` is called by the device thread when a host timer fires, and the VP thread never stops for a timer.
- Deliver the wheel's outputs through the hypervisor LAPIC: IOAPIC/MSI edges → `WHvRequestInterrupt` (OpenVMM `assert_irq`, crosvm `send_msi`, Hyperlight timer); PIC/ExtInt → `PendingEvent`/`PendingInterruption` gated by `DeliverabilityNotifications` (OpenVMM `inject_extint`, crosvm `inject_interrupts`). That is what lets the VP stay in `WHvRunVirtualProcessor` for whole scheduling quanta and is the single biggest difference from applepie and from our current 3.8 %-on-hardware engine.
- Our `LocalApicEmulationMode::None` + own LAPIC puts us on OpenVMM's *opt-in* `user_mode_apic` path, whose interrupts cannot reach a running VP without a cancel — applepie's problem in a different coat. Switching to XApic/X2Apic mode is the precondition for the pattern above.
- The shadow interpreter stays useful only for what applepie used it for — SMM/SMI, unsupported features, `InvalidVpRegisterValue` recovery, instrumentation — not as the interrupt-delivery path or the MMIO emulator; OpenVMM's per-exit `WhpEmuCache` (one batched Get, one batched Set, exit-context instruction bytes) is the register-sync budget to match.
- applepie never produced a throughput number; the only comparable measurement is wtf's "whv ~10x slower than KVM" for a no-device VP, i.e. even a device-free WHP loop with per-register IOCTLs is an order of magnitude off KVM — so the sync budget per exit, not just the exit count, has to be designed down.
