# Plan review — test design and measurement

Plan: `docs/superpowers/plans/2026-09-03-whp-vmm-shape.md`. Spec: `docs/superpowers/specs/2026-09-03-whp-vmm-shape-design.md`.
Read-only review. Line cites are plan line numbers unless a source file is named.

## 1

- [blocking] Task 1.7 Step 1, `step_in_ticks_runs_the_guest_for_that_much_vm_time_and_pauses` (plan:1000) — the arithmetic does not say what the comment says, and its direction is inverted. `counters.runtime.hypervisor_100ns() * 10 >= 9 * 10_000 * 10 / 10` reduces to `hypervisor_100ns >= 9_000`, i.e. **0.9 ms**, not the 9 ms the comment claims (9 ms = 90_000 units of 100 ns) — a 10× error. Worse, `HypervisorRuntime100ns` is the hypervisor's *overhead* share, not in-guest time: `rusty_box_whp/src/partition.rs:395-400` says so verbatim ("how much of that the hypervisor spent on its behalf rather than running its guest. The difference between the two is guest time"). For the `jmp $` guest the honest value is near zero, so a correct implementation FAILS this assertion and a pathological one passes. Write instead: `let guest = counters.runtime.total_100ns - counters.runtime.hypervisor_100ns; assert!(guest >= 90_000, "≥ 9 ms of the 10 ms was guest time, not hypervisor overhead: {counters:?}")`. (Also `hypervisor_100ns` is a field, not a method.)
- [blocking] Task 1.7 Step 1, `a_guest_that_halts_stays_parked_in_the_hypervisor_and_wakes_for_a_device_interrupt` (plan:1006) — the body is prose only; an empty `#[test]` cannot fail and violates CLAUDE.md's no-stub rule. Either write the guest and the two assertions (MARK count at the PIT rate; `exits_total() ≈ MARKs`, with the "≈" pinned as `exits <= marks + 2`) or delete it from the plan.
- [blocking] Task 0.2 Step 2, `the_apic_state_page_addresses_registers_at_offset_shifted_by_four` (plan:249) — the expression and its own comment disagree by 16×, and the expression is the wrong one. `page.0[0x80 << 4 - 4 + 4 ..]` parses as `0x80 << 4` = byte **0x800**; the comment says "field index = 0x80 >> 4 = 8, ×16 bytes" = byte **0x80**. The comment is right: the page is QEMU's `whpx_lapic_state` shape — one 32-bit field padded to 16 bytes, indexed by `reg >> 4` — so the byte offset **equals** the xAPIC MMIO offset. The spec's §3.3 wording "register offsets `<< 4`" (spec:250) is the source of the error and should be corrected to "index = offset >> 4, 16-byte stride, so the byte offset is the register's MMIO offset". As written this test cements a 16×-shifted table — exactly the failure CLAUDE.md names ("a test written on top of a wrong table cements the bug"). Assert `page.0[0x80..0x84] == 0xF0u32.to_le_bytes()` and add `assert_eq!(page.0[0x84..0x90], [0; 12], "the 12 pad bytes stay zero")` so a stride mutation is caught.
- [blocking] Task 1.6 Step 1, `an_ioapic_edge_is_delivered_by_the_hypervisor_apic_without_an_exit` (plan:948) — `assert_eq!(exits_before, 1)` cannot hold. IOAPIC stays trapped MMIO under this design (spec:363), so the guest's own IOAPIC programming is ≥ 4 `MemoryAccess` exits (IOREGSEL+IOWIN for the low and high dwords), plus the MARK port exit; only the SVR/EOI writes to the hypervisor-owned LAPIC page are exit-free. Expected total ≥ 5, and it is a *cumulative* count so it also folds in anything the harness did. Assert the delta instead: snapshot `exits_total()` immediately before `irq.raise(...)`, then `assert_eq!(after - before, 1, "the delivery itself cost no exit; the only exit is the handler's MARK write")`. That delta is mutation-sensitive (a fallback to `DeliveryRoute::Model` + cancel + inject would show ≥ 2).
- [major] Task 1.3 Step 1, `service_device_time_fires_due_timers_and_names_the_next_deadline` (plan:614) — cannot detect the coalescing mutation the plan itself names as the hazard (plan:625: a single `countdown_event` after a large jump coalesces a periodic timer's missed fires). Both assertions survive it: `time_ticks()` still advances by the full 1_000_000, and `next.is_some_and(|t| t > before + 1_000_000)` is satisfied by any armed timer whatsoever. Add the fire count here, not only in Task 1.7: `assert_eq!(machine.keyboard_timer_fires_seen(), 22, "1_000_000 ticks / 45_000 = 22 serial-delay periods, each fired, none coalesced")`, and pin the deadline exactly (`before + 1_000_000 + 45_000 - remainder`) rather than `>`.
- [major] Task 1.5 Step 1, `a_park_request_made_between_runs_is_seen_before_the_next_run` (plan:868) — the doc comment claims the QEMU ordering property (flag first, then cancel, so a request raised between runs is never lost), but the two assertions are order-blind: swap the two statements inside `request_park` and the test still passes. Make the recording canceller capture `exit_requested` at the moment `cancel()` is called and assert `control.flag_seen_by_cancel() == true`.
- [major] Task 1.4 Step 1 — no test guards the clobber direction, which is the whole point of `fExtrn`. Every assertion counts reads/writes; none asserts that a group the exit did NOT import keeps the partition's live value. Mutation: make `export_imported` write `Externalised::all()` — every existing assertion except `writes_of(Reg::Es) == 0` still passes, and that one is only checked in the first test. Add: import `Cpuid`, mutate the shadow's `DS` and `CR3` locally, export, then `assert_eq!(vp.value_of(Reg::Es), the_value_the_recorder_was_seeded_with, "a group this exit never imported is not written back over")`.
- [major] Task 1.4 Step 5 (plan:766) — the segment-validity test has no negative control. A rule that refuses "present && attributes == 0 && limit == 0xFFFFF" must be shown NOT to refuse the legitimate cases: a real-mode segment (attributes 0x93, limit 0xFFFF) and a genuinely unused segment (`present == false`, attributes 0). Without those, the rule can be tightened into one that rejects every guest and the suite stays green.
- [minor] Task 0.2 Step 2, `the_openvmm_vtl0_synthetic_set_is_every_named_flag_and_nothing_else` (plan:264) — `assert_eq!(OPENVMM_VTL0, SyntheticFeatures::all())` compares the composite against the union of the flags it is literally defined as; it can only fail if a future flag is added without being added to the composite. That is a useful ratchet, but it is not a check of the header's set. The `iter_names().count() == 22` line is the one that can catch a dropped constituent; keep both and say so.
- [minor] Task 1.2's three `VmTime` tests are sound and mutation-sensitive (a `start()` that fails to re-anchor gives 10_700 instead of 1_000; `u64` intermediates overflow the `u64::MAX / 4` round trip, which I checked is exact at rate 300 MHz). No change.

## 2

- [major] Task 0.2 Step 5, `the_apic_state_page_round_trips_through_the_platform` (plan:319) — the name promises a round trip and P2 (spec:452) promises "page → model → page, bit-identical", but the body only reads once and writes once; nothing compares. Add the third call and the comparison: `let mut back = ApicStatePage::zeroed(); vcpu.read_apic_state(&mut back)?; assert_eq!(page.0[..1024], back.0[..1024], "the first KiB the model owns survives the round trip")`. Without it, a `write_apic_state` that silently discards the buffer passes.
- [major] Task 0.2 Step 5 — `assert_eq!(page.register(0x30) & 0xFF, 0x14)` guesses the hypervisor's LAPIC version. It is unverified for Hyper-V's synthetic APIC (Intel xAPIC reports 0x14/0x15; Hyper-V is not established by any report cited). If it is wrong the plan blocks on an incidental at Task 0.2. Assert the property actually wanted — the page came back populated, not zeroed — as `assert_ne!(page.register(0x30), 0, "a fresh VP's version register is populated; the page is not a zero buffer")`, and RECORD the observed version in the P2 section of the probe document rather than asserting it.
- [minor] Task 1.5 Step 1's hypervisor-free protocol test asserts implementation detail (an atomic and a cancel count), not a guest-visible property. Acceptable as a protocol unit test under R9's normal latitude, but its guest-visible sibling — the gated `a_vcpu_thread_services_a_port_exit_under_the_machine_lock` — is what actually earns R9, so keep both and let the commit message say which is which.
- [minor] Task 0.2 Step 2's four encoding tests and Task 1.4's `Externalised` algebra tests are pure encoding checks in and around the FFI leaf; that is the acceptable place for them (`vcpu.rs`/`caps.rs` are the leaf, `exchange.rs` is one step above it). No change. The one encoding test that is NOT in the leaf and should be guest-visible is `lvt0_gates_the_legacy_path_the_way_the_lapic_would` (plan:928): it asserts a predicate over a register word. Its guest-visible sibling is missing — a gated test where a guest masks LVT0, the fabric raises an ExtINT, and the guest's handler does NOT run — and P5's second half (plan:364) is exactly the measurement that decides whether that sibling is a fidelity nicety or a correctness requirement. Name the sibling in Task 1.6 conditional on P5's answer.

## 3

- [blocking] `VcpuControl::wait_parked(&self) -> Parked` (plan:786) has no timeout, and Task 1.5/1.6/1.7's gated tests call it directly. A vCPU thread wedged inside `WHvRunVirtualProcessor` (a cancel that did not stick — the design itself says stickiness is undocumented, spec:122) makes `wait_parked` block forever while holding the `a_turn_on_the_hardware` mutex, hanging the whole libtest process and starving every other gated test. Give it `wait_parked_by(&self, deadline: Duration) -> Option<Parked>` and have the tests `expect("the thread parked within 5 s — a cancel that never stuck")`. Same for the bare `join.join().unwrap()` that follows each one.
- [blocking] `FastMachine::step(RunBudget::Ticks(n))` (plan:1012) waits on a condvar "until `clock.now() ≥ start + n` or a vcpu parked" — no wall-clock bound. Today `step` is bounded by the slice engine, and `alpine_probe`'s patience check runs BETWEEN steps (`alpine_probe.rs:269`), so a wedged vCPU thread makes the 300 s patience unreachable and the baseline run hangs instead of reporting. `step` needs its own wall deadline (e.g. 10× the tick budget's nominal duration, floor 1 s) surfacing as a named refusal that `alpine_probe` prints and exits on.
- [blocking] `wait_until(...)` (plan:875, plan:955) does not exist anywhere in the tree (checked: no hit in any `.rs`). Its timeout semantics are unspecified — whether it returns `bool`, panics, or loops. Define it once in the engine's test module as `fn wait_until(mut done: impl FnMut() -> bool, within: Duration, what: &str)` that panics with `what` on expiry, so a guest that never writes the port fails **by name** rather than by the harness's own 60 s libtest kill.
- [blocking] `debug_port().peek_output()` (plan:875, plan:955) does not exist — only the draining `take_output()` (`rusty_box/src/emulator_api.rs:104`). A `wait_until` polling loop built on `take_output` drains the byte it is waiting for and spins forever. Either add a non-draining peek or have the closure accumulate into a `Vec` the assertion then inspects, as `trace_of` already does (`rusty_box_whp_engine/src/lib.rs:171-190`).
- [major] Task 0.3 P1/P3/P4/P5 rescues are 200 ms (plan:352, 360, 362) and follow `whp_probe.rs`'s `run_with_rescue` pattern, which is correctly bounded and reports `rescued` — good. But P1 (plan:352) runs the guest a SECOND time after the injection with another 200 ms rescue and reports only "did MARK arrive". If neither run produces MARK the probe must record which run ended how; state the required output as a table row per run (`exit reason`, `elapsed`, `rescued`) so "never woke" is distinguishable from "woke on the wrong run".
- [major] Task 0.2 Step 5 and Task 1.1 Step 1's gated tests use `hypervisor_present().unwrap_or(false)` / `hypervisor_here()` and `a_turn_on_the_hardware()` correctly, but Task 0.2's own note (plan:332) is unsure whether `a_turn_on_the_hardware` exists in `rusty_box_whp`. It does — `rusty_box_whp/src/partition.rs` uses it at :1268. Drop the hedge; do not add a second copy, which would defeat the one-partition-per-process rule.
- [minor] Task 1.7 `FastMachine::pause` (plan:1011) calls `wait_parked` per vCPU with the same unbounded wait, and `Drop` (plan:1016) does "pause; stop; join every thread". A wedged thread therefore hangs the DROP of every gated test's machine, after the assertions passed. Bound the drop path too and report rather than block.

## 4

- [blocking] Task 1.6 Step 1, `an_ioapic_edge_is_delivered_by_the_hypervisor_apic_without_an_exit` (plan:952) — the guest programs "IOAPIC entry 2" but the harness raises `IrqLine::new(0)`, and this tree maps an ISA line to the IOAPIC pin of the SAME number: `IrqFabric::set_isa_level` calls `self.set_ioapic_pin(line.0, level)` (`rusty_box/src/iodev/irq.rs:121-126`) — there is no IRQ0-to-pin-2 override. Raising line 0 drives pin 0, entry 2 never fires, MARK never arrives, and the test hangs in the undefined `wait_until` (see section 3). Either program entry 0 or raise `IrqLine(2)`; the comment "PIT line → IOAPIC pin 2" is wrong for this port either way. Also `IrqLine` is a tuple struct used as `IrqLine(1)` in `irq.rs`'s own tests — `IrqLine::new` may not exist.
- [blocking] Task 1.6 Step 1 — the same test is unreachable from where it is placed. `IrqFabric::raise`, `set_ioapic_pin`, `line_level` are all `pub(crate)` in `rusty_box` (irq.rs:121-152), and `Emulator::cpu_ref` is `pub(crate)` (`rusty_box/src/emulator/mod.rs:594`). A test in `rusty_box_whp_engine/src/lib.rs` is a different crate and cannot call any of them. Either the raise goes through a public verb (a device that asserts the line, or a new public `Emulator::raise_isa_line` justified as a test seam) or the test moves into `rusty_box`. Task 1.3's `machine.cpu_ref(0).lapic.vector_state(0x31)` IS inside `rusty_box`, so that one is fine.
- [major] Task 1.6 Step 1, `IOAPIC_EDGE_GUEST` (plan:958) — "~40 bytes" covers only the mode switch, and the plan gives no budget or placement for the rest. A working guest needs, beyond the ~25-32 bytes of `lgdt`/`mov cr0`/far jmp/flat DS: a GDT and an IDT in memory (the harness `machine_with_devices` writes code at `CODE = 0x1000` and nothing else — `rusty_box_whp_engine/src/lib.rs:150-165`), an IDT gate for 0x40, `lidt`, the SVR write (10 bytes), four `mov dword [0xFEC0xxxx], imm32` IOAPIC writes (~40 bytes), `sti`, `jmp $`, and a handler with MARK + EOI + `iretd` (~16 bytes). Realistic total is 130-160 bytes of code plus two descriptor tables. State that, and name the addresses the tables go at, or the task gets re-scoped mid-implementation.
- [major] Task 1.5 Step 1's gated test (plan:872) — the guest `[0xB0, MARK, 0xE6, DEBUG_PORT, 0xF4]` decodes correctly (`mov al,0x5A; out 0xE9,al; hlt`), but it collides with the `Halt` arm this very task defines. Task 1.5 lands before Task 1.6, so the partition is still `LocalApicMode::None`, where `Halt` exits DO occur; the arm is specified as "per P3's answer: if P3 said never in APIC mode, `Fault(UnexpectedHalt)`" (plan:864). A thread that faults on the halt makes `wait_parked()` return `Fault`, and `assert!(matches!(..., Parked::Paused))` fails. Either the guest ends in `jmp $`, or the `Halt` arm re-enters until Task 1.6 flips the mode — say which, in the plan.
- [minor] Task 1.7's `[0xEB, 0xFE]` is `jmp $` — correct. Task 0.3 P1's `sti; hlt; hlt` and P3's `cli; hlt` are correct for what they test.
- [minor] Task 1.6 Step 1 — `control.census()` is called on `VcpuControl`, but the produced `VcpuControl` (plan:781) has no census field; the census lives on `VcpuThread`, which the spawned thread owns. Cross-thread census access is not designed. Either the census becomes shared atomics inside `VcpuControl`, or the assertion reads it through the machine after the park.
- [minor] Task 1.4's tests pass a `Recorder` where `Exchange`'s signatures take `&Vcpu` (plan:743-747) — they cannot compile. `Exchange` must be generic over `state::VpRegisters` (the trait already exists, `state.rs:138`), which is also what R8 requires instead of `dyn`. And `Recorder` is a private item of `state.rs`'s `#[cfg(test)] mod tests` (`state.rs:417-427`) — unreachable from `exchange.rs`; it must be promoted to a `#[cfg(test)] pub(crate)` module. `test_cpu()`, `XsaveArea::for_tests()`, `VpContext::for_tests()` and `ApicStatePage::zeroed()` do not exist and are in no Produces block.

## 5

- [blocking] G1 (spec:468, plan:1041) reads the wrong counter in the wrong direction. `HypervisorRuntime100ns` is the hypervisor's overhead share of `TotalRuntime100ns` — this tree's own doc says the difference is guest time (`rusty_box_whp/src/partition.rs:395-400`) — so `HypervisorRuntime100ns / wall >= 90 %` asks for 90 % OVERHEAD. `alpine_probe` already prints it under the honest name `hypervisor_ms` beside `runtime_total_ms` (`alpine_probe.rs:310-319`); the plan's `in_run_share = hypervisor_ms/wall_ms` (plan:1030) inherits the inversion. The corrected expression from these two counters is `(total_100ns - hypervisor_100ns) / total_100ns`.
- [blocking] Even corrected, neither counter is wall time. `TotalRuntime100ns` accrues only while the VP is scheduled; a VP halted inside `WHvRunVirtualProcessor` or descheduled by the host accrues nothing, so `total/wall < 1` for reasons unrelated to the design. G1's second half — "idle-at-login exits/s in the low thousands" — is exactly the idle regime where this metric collapses. The gate states "≥ 90 % of busy wall time inside `WHvRunVirtualProcessor`" (plan:5), so measure that literally: accumulate `Instant::now()` deltas around `vcpu.run()` in `VcpuThread`'s census (`in_run_nanos`, `runs`), publish through `engine_census()`, and use the runtime counters only as a cross-check that the two agree.
- [blocking] The counters are cumulative since VP creation and `alpine_probe` reads them ONCE at the end (`alpine_probe.rs:306`). A share "over the kernel phase" needs a sample at each end of the window and a difference. Task 1.8 Step 1 adds `in_run_share` to the 10-second report and the final line — both cumulative-from-boot, which is not the windowed quantity G1 names. Sample `(wall, in_run_nanos, total_100ns, hypervisor_100ns)` at every milestone hit (`alpine_probe.rs:225-232` already has the hook) and print `RESULT in_run_share phase=A..B share=X`.
- [major] "the kernel phase (ISOLINUX exit → `login:`)" is not detectable from the scrape. `MILESTONES` (`alpine_probe.rs:61-69`) records the first APPEARANCE of `"ISOLINUX"`, never its exit. Use `"Linux version"` — the next milestone, and the actual start of the kernel phase — as the window start, and say so in the gate. As written G1 is unjudgeable.
- [major] Task 1.9's "wall < the interpreter's median from the baseline document" is not like-for-like. The interpreter baseline is taken with `alpine_bench` (Task 0.1 Step 4) and the WHP number with `alpine_probe` (Step 2) — different harnesses, different step budgets, different scrape cadence, so their wall clocks carry different harness overhead. Step 4 also prescribes ONE interpreter run while Task 1.9 compares against a MEDIAN. Fix both: three interpreter runs through `alpine_probe` with `ALPINE_ENGINE=interpreter`, median taken there.
- [minor] Task 1.8 Step 1 says "keep every printed `RESULT` line's name so the baseline document's columns still apply", but Task 1.7 deletes the slice engine and `census.slices` (`alpine_probe.rs:249`) becomes meaningless. Say what replaces that column (runs entered, exits by class) rather than printing a zero that reads as a measurement.
- [minor] Task 1.9's "zero fatal signatures (no `Oops`, no `general protection`) in the scraped screen" — the scrape is the CURRENT 80x25 text buffer, sampled once per step (`alpine_probe.rs:224`). A panic that scrolls off between two samples is invisible. Accumulate the union of distinct lines seen, or scan the serial capture, and assert on that.

## 6

- [blocking] Task 0.1 Step 2 (plan:73) names the ISO as "the Alpine ISO used on 2026-09-01" — which the plan's own Global Constraints (plan:17) say was a NO-QUIET copy whose numbers are explicitly disqualified. The step points at the wrong file. Name the original quiet ISO, and have the baseline document record the ISO's file name and SHA-256 so every later comparison can prove it used the same one.
- [major] Task 0.1 Step 4b (plan:86) — the W7 row has no defined start/stop. The prose names three points ("power-on → boot logo → edition-selection wizard"); the table column names two ("power-on → edition wizard"). The only prior figure is "6-8 minutes FROM THE LOGO" (spec:61), so without a logo timestamp the new number cannot be compared to the old one at all. Define start = the click on "Power On VM", and record BOTH the first frame showing the boot logo and the first frame showing the edition list, as two columns.
- [major] Task 0.1 controls for the ISO and for GUI-vs-step-driven (Alpine and DLX headless and step-driven; W7 is GUI on both sides of G3), but not for host contention. Nothing says to close other VMs or to check that no `cargo build` is running, and nothing records host load — yet `alpine_probe` spawns a CPU-hungry alarm thread (plan:71 acknowledges this for concurrency only), and the spec's own risk list notes WHP throughput moved 70 % between host builds (spec:561). Add to the baseline document header: Windows build, whether Defender real-time scanning was on, whether any other hypervisor partition existed, and a statement that no build ran concurrently.
- [minor] Task 0.1 Step 5's table has no row for the head engine's exit counts or its corrected in-run share, so Task 1.9's mechanism gate has an after with no before. Add an "in-run share (guest/total)" row and an "exits by class" row at head.
